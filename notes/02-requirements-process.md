# 02 要件定義の進め方

## 1. 今回の流れ
```
お客さん（Aさん）の話を聞く（ヒアリング）
  → 機能を「最初に作る」「将来」「対象外」に分ける
  → 操作の流れ（ユースケース）を決める
  → 画面のスケッチを描く
  → 要件定義書にまとめる（内容ごとに、ドキュメントを分ける）
  → プロトタイプを作って、動かして確認する
  → 足りなかったこと、使いにくかったことを、要件定義書に反映する
```
要件定義書は、一度で完成させるものではなく、**確認しながら育てていくもの**。

## 2. ドキュメントの構成（docs/）

| ファイル | 役割 | 一言で言うと |
|---|---|---|
| requirements.md | 要件定義書（ハブ）。背景・目的、利用者、各ドキュメントへのリンク、受け入れ条件 | **全体の入口** |
| functional-requirements.md | 機能一覧（最初に作る／将来／対象外） | **何ができるか** |
| use-cases.md | ユースケース（操作の流れ） | **どう使うか** |
| screen-design.md | 画面設計 | **どう見えるか** |
| non-functional-requirements.md | 非機能要件 | **どんな条件で動くか** |
| data-design.md | データ設計（ER図） | **何を保存するか** |
| tech-stack.md | 技術スタック | **何で作るか** |

### 分ける理由
- 同じ内容を**2か所に書かない**（食い違いを防ぐ。Single Source of Truth）
- 読む人に合わせて、必要なところだけ読める
- 変更の履歴が、目的ごとに追える

## 3. 用語

| 用語 | 意味 | 今回の例 |
|---|---|---|
| 機能要件 | アプリが「できること」 | カードの追加、ドラッグ＆ドロップ、期限日 |
| 非機能要件 | 「どんな条件で、どれくらいの品質で動くか」 | Windows・Chrome、最大500枚で動く、自動で保存される |
| ユースケース | 利用者が、目的を達成するまでの操作の流れ | UC-1：カードを追加する |
| 例外の流れ | うまくいかない場合、入力を間違えた場合の動き | 空のままEnterを押したら、カードは作られない |
| 画面設計 | 画面の構成、表示、操作 | 3つの列、マウスオーバーで出るアイコン |
| ER図 | データと、データ同士の関係を表す図 | 列とカードの関係 |
| 受け入れ条件 | 何ができたら「完成」と認めるか | ブラウザを閉じてもカードが消えない |
| スコープ | 作る範囲 | 「最初に作る」「将来」「対象外」 |
| スコープクリープ | 作る範囲が、いつの間にか広がること | 要望にない「コピー機能」を勝手に足さない |

## 4. 現場で大事な考え方（今回学んだこと）

| 考え方 | 例 |
|---|---|
| **あいまいな言葉を、具体的にする** | 「一目で分かる」→「3つの列と各列のカードが、1つの画面に表示される」 |
| **数字で書く** | 「たくさん」→「通常100枚、最大500枚」 |
| **その数字を超えたらどうなるかも、決める** | 500枚は目安で、超えても追加できる |
| **「作らないもの」も決める** | ログイン、複数ボード、自動バックアップなど |
| **取り返しのつかない操作には、確認を入れる** | 削除、バックアップの読み込み |
| **よく使う操作は、押しやすく。まれな操作は、奥に** | 色・期限は、マウスオーバーで直接。削除は、メニューの中 |
| **操作の回数も、使いやすさの一部** | 「移動ボタン→列を選ぶ」より、ドラッグ＆ドロップ |
| **お客さんの案を受け止めつつ、提案もする** | モーダルより、カードの近くの小さな窓のほうが、変化が見える |
| **機能同士の依存関係を意識する** | 「期限順の並び替え」は、「期限日」が先に必要 |
| **仮定を示して、合意を取る** | 「こうする想定ですが、よいですか？」と聞く |
| **難しさではなく、お客さんにとっての価値で、優先順位を決める** | ドラッグ＆ドロップを、最初に作る機能に入れた |
| **開発者が勝手に足したことは、明示して確認する** | PRの説明に「確認してほしい点」を書く |
| **要件と設計を、区別する** | カラーコードは、要件定義書ではなく、設計・実装で決める |

## 5. プロトタイプで分かったこと
動かしてみて、初めて気づいたことがあった。要件定義の段階だけでは、見つけにくい。

- 入力欄の外をクリックしたとき、どうなるか（文字があれば確定、空なら消える）
- 取り消し方が、画面から分かりにくい → 案内を表示する
- カレンダーの出る位置が、バラバラ → 自作して、位置をそろえた
- `10/12` が、「12枚中の10番目」に見える → 「期限 10月12日」に変更
- 絵文字のアイコンが、全体の色と合わない → 線画のアイコンに統一

## 6. やってみよう
1. `docs/requirements.md` を開き、各ドキュメントへのリンクをたどってみる
2. `docs/use-cases.md` の「例外の流れ」を、プロトタイプで、実際に試す
3. 「こういう機能があったら便利」と思いついたら、まず「将来の機能」に書き足してみる
