## 1. 道具の役割
| 道具 | 役割 | たとえ |
|---|---|---|
| Node.js | JavaScript を、ブラウザの外で動かす土台 | 厨房の電気・ガス |
| npm | 部品（ライブラリ）を入れたり、コマンドを実行したりする | 食材の仕入れ係 |
| Vite | 開発用のサーバーと、本番用のビルドをする | 試食用の仮設キッチン |

## 2. 画面が、データを表示するまでの流れ
```
ブラウザ → (5173番) Vite → /api/... は、そのまま (8080番) バックエンドへ中継 → DB
```
1. 画面を開くと、`App` が `useBoard` を呼ぶ（同時に、背景のために `useSettings` と `useBackgroundImages` も、設定と画像の一覧を取りにいく）
2. `useBoard` が、`/api/columns`（列）と `/api/cards`（カード）を、同時に取りにいく
3. 結果を、`Board` → `BoardColumn` → `CardItem` の順に渡して、表示する
4. カードを追加・編集・移動したときは、APIにお願いして、成功したら `reload()` で取り直す（ドラッグ＆ドロップは、先に画面を動かしてから保存する。10章）

### なぜ、プロキシ（中継）を使うのか
- 画面（5173番）から、別の場所（8080番）に直接お願いすると、ブラウザが、安全のために止める（**CORS**）
- Vite に「`/api` は、8080番に回して」と設定（`vite.config.ts` の `proxy`）すると、ブラウザには「同じ場所とのやりとり」に見える
- そのため、バックエンドに、CORS の設定を足さずに済む
- バックエンドが止まっているときは、プロキシが `502` を返す。画面では「サーバーに接続できません」と表示する

## 3. フォルダの構成（`frontend/src/`）
| 場所 | 役割 |
|---|---|
| `api/types.ts` | APIが返すデータの「型」（バックエンドの Response と同じ形） |
| `App.tsx` | 画面全体。ヘッダー（検索、背景、バックアップ）、背景の層、ボードを組み合わせる |
| `api/client.ts` | APIを呼ぶ関数（取得 `fetchCards` など、追加 `createCard`、更新 `updateCard`、削除 `deleteCard`、移動 `moveCard`、期限順 `sortColumnByDue`、バックアップ `fetchBackup` / `restoreBackup`、設定 `fetchSettings` / `updateSettings`、自分の画像 `fetchBackgroundImages` など）。失敗したときの、分かりやすいエラーメッセージも作る |
| `hooks/useBoard.ts` | 列とカードを取得して、「読み込み中／エラー／成功」を管理する。`reload()` で取り直せる |
| `hooks/useSettings.ts` | 選んだ背景の取得と保存。自動（時間帯）の見直し |
| `hooks/useBackgroundImages.ts` | 自分の背景画像の取得・登録・削除 |
| `hooks/usePopover.ts` | ボタンの下に開く小さな窓（カレンダー、背景の選択）の、位置決めと閉じる処理 |
| `components/` | 画面の部品。ボード：Board、BoardColumn、CardItem ／ カード：CardComposer、CardModal、ColorPicker、DuePicker、Calendar ／ 検索：SearchBar ／ バックアップ：BackupControls、ConfirmDialog ／ 背景：BackgroundPicker、BackgroundLayer |
| `lib/date.ts` | 期限の表示（「期限 10月15日」）と、期限切れの判定 |
| `lib/calendar.ts` | カレンダーの計算（6週間分の日付、前後の月） |
| `lib/moveCard.ts` | カードを動かした結果の計算（別の列へ、同じ列の中で。position の連番の振り直し）。画面を使わない「ただの関数」 |
| `lib/dragIds.ts` | ドラッグ＆ドロップで使う目印（`card-1`、`column-1`）。カードと列のIDが同じ数字でも、区別できるようにする |
| `lib/cardColors.ts` | カードの色（6色）の定義。色を変えるときは、ここの1か所 |
| `lib/backup.ts` | バックアップのファイル名（日時つき）、ファイルの軽い検査、JSONの保存 |
| `lib/background.ts` | 背景の選択肢、自動（時間帯）の判定、列の色合い |
| `lib/image.ts` | 画像の種類と大きさの判定、横1920pxへの縮小 |
| `index.css` | 背景の見た目（標準の画像と、代わりのグラデーション） |
| `public/backgrounds/` | 標準の背景画像3枚と、出どころを書いた `CREDITS.md` |

**画面を使わない関数（`lib/`）に、計算や判定を切り出す**のが、この画面の作り方の特徴。画面の部品（`components/`）から離しておくと、境目の値（4:59 と 5:00 など）を、単体テストで確かめやすい。

## 4. 学んだポイント
- **状態（state）**：画面が覚えている値。値が変わると、React が画面を描き直す
- **日付は、文字列のまま比べる**：`'2026-10-12' < '2026-10-15'` のように、同じ形（YYYY-MM-DD）なら、そのまま日付の順に比べられる。`Date` を使うと、時差でずれることがある
- **古い結果で上書きしない**：検索を続けて行うと、前の問い合わせの結果が、あとから届くことがある。`useBoard` は、条件ごとに結果を持ち、今の条件のものだけを使う
- **テストの片付け**：Vitest では、テストのあとに、描いた画面を自分で片付ける（`cleanup`）。忘れると、前のテストの画面が残って、「同じ要素が複数ある」と失敗する
- **Tailwind の指定がぶつかる**：`bg-white` と `bg-[#4f7cff]` を同時に付けると、どちらが勝つかは、CSSの並び順で決まる。ボタンの文字が読めなくなったのは、これが原因だった。背景色は、1つだけ付ける
- **`strictPort`**：Vite は、5173番が使えないと、黙って別の番号で起動する。`strictPort: true` で、失敗させる。ただし、他のプロセスが全アドレス（`::`）で5173番を握っていると、気づけない。起動前の確認が必要（スキル `dev-port-conflict`）

## 5. やってみよう
1. `docker compose up -d` → `backend/` で `.\gradlew.bat bootRun` → `frontend/` で `npm run dev` の順に起動する
2. http://localhost:5173 を開き、3列にカードが並ぶのを確認する
3. 「キーワード」に「買」と入れて、「検索」を押す → カードが2枚に絞られる
4. 「期限（この日まで）」に日付を入れて検索する → 期限のないカードは、出てこない
5. バックエンドを止めて、画面を開き直す → エラーが表示される

## 6. カードの新規登録（画面から追加する）
流れ：列の「＋」→ `CardComposer`（入力欄）→ Enter → `createCard` が `POST /api/cards` → 成功したら `reload()` でボードを取り直す → 新しいカードが、列の一番上に出る。

- **GET と POST の違い**：取得（GET）は URL だけでよいが、追加（POST）は「送る中身」が要る。`fetch(url, { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify(入力) })` の形で送る
- **画面を直接書き換えず、取り直す**：追加したカードを自分で画面の一覧に足すこともできるが、並び順や ID の決定はバックエンドの役目。そのため、追加後はサーバーから取り直して、**サーバーの結果を正とする**
- **入力欄の外を押したとき**：`onBlur`（フォーカスが外れた）で、入力済みなら追加、空なら閉じる。ただし、色のボタンや期限欄を触っただけで閉じないよう、移動先が入力欄の中なら無視する（`relatedTarget`）。色ボタンは `onMouseDown` で `preventDefault()` して、フォーカスを奪わない
- **日本語入力の Enter**：漢字に変換して確定する Enter で、追加されてしまわないよう、`isComposing`（変換中）のときは無視する
- **二重送信の防止**：Enter とフォーカス外れが重なっても、2回送らないよう、`useRef` で「送信中」を覚えておく
- **失敗したとき**：400（タイトルが空・長すぎる）などは、エラーを表示して、入力欄と入力内容は残す

### やってみよう
1. 3つのサーバーを起動して、http://localhost:5173 を開く
2. ToDo 列の「＋」を押し、タイトルを入れて Enter → 一番上に出る。ページを再読み込みしても残る（DBに保存された）
3. 色の丸と期限の日付を選んで追加する → 背景色と「期限 ○月○日」が付く
4. Esc で取り消す／空のまま Enter を押す → 何も追加されずに閉じる

## 7. カードの編集（モーダル）
流れ：カードを押す → `Board` が「開いているカード」を覚える → `CardModal`（窓）が開く → 「保存」→ `updateCard` が `PUT /api/cards/{id}` → 成功したら `reload()` で取り直して、窓を閉じる。

| 部品 | 役割 |
|---|---|
| `CardItem` | カード全体を `button` にして、押せるようにした。説明文があれば、三本線の目印を出す |
| `Board` | どのカードを編集中かを、`useState` で持つ。`CardModal` を出し入れする |
| `CardModal` | 窓の本体。タイトル・説明文・色・期限を、窓の中だけの状態として持つ |
| `ColorPicker` | 色見本。追加の入力欄（`CardComposer`）と窓で、**同じ部品を使い回す** |

- **窓の中の入力は「下書き」**：入力した内容は、窓の中の状態にだけ入る。「保存」を押すまで、サーバーにも、ボードにも、届かない。だから、キャンセル・Esc・窓の外を押すだけで、変更を捨てられる
- **変更がなければ通信しない**：元のカードの内容と見比べて、同じなら、`PUT` を送らずに閉じる
- **空の値は「なし」**：説明文を消す、期限を外す、は `null` にして送る（バックエンドの仕様）。空白だけの説明文も `null` にそろえる
- **保存できない条件**：タイトルが空（空白だけ）のあいだは、「保存」ボタンを押せなくして、Enter でも送らない。保存中も二重に送らない（`useRef`）
- **失敗したとき**：窓を閉じずに、エラーを表示する。入力した内容は残るので、直してもう一度押せる
- **窓の外（暗い部分）を押して閉じる**：`onMouseDown` で、`e.target === e.currentTarget`（窓の外そのものを押した）ときだけ閉じる。窓の中の押下が、外に伝わって閉じてしまうのを防ぐ
- **Esc キー**：窓が開いている間だけ、`document` に `keydown` を付ける。`useEffect` の片付け（`return`）で、閉じたら外す
- **`key` を付ける理由**：`<CardModal key={editing.id}>` で、別のカードを開いたとき、前のカードの入力が残らないように、作り直す
- **テストは、画面全体を動かす**：`CardModal.test.tsx` は `App` を描いて、通信（`fetch`）だけをモックに替える。「押す→入力→保存→ボードに反映」を、ユーザーと同じ順番で確かめられる
- まだ作っていないもの：削除ボタン（14の回）。期限の自作カレンダーは、次の章（8章）で作った

### やってみよう
1. 3つのサーバーを起動して、http://localhost:5173 を開く
2. カードを押して、タイトル・説明文・色・期限を変えて保存する → ボードに反映され、再読み込みしても残る
3. 説明文を付けたカードに、三本線の目印が出ることを確かめる
4. 編集の途中で、キャンセル・Esc・窓の外を押す → 変更が捨てられる
5. タイトルを空にする → 「保存」が押せなくなる
6. バックエンドを止めて保存する → エラーが出て、窓が開いたままになる

## 8. 自作カレンダー（期限日）
期限の欄（`DuePicker`）を押すと、カレンダー（`Calendar`）が開く。編集のモーダルと、カード追加の入力欄の、両方で使う。

| ファイル | 役割 |
|---|---|
| `lib/calendar.ts` | カレンダーの計算（6週間分の日付、前の月・次の月）。画面を使わない「ただの関数」 |
| `components/Calendar.tsx` | カレンダーの見た目と操作（＜＞、曜日、日付、「期限を外す」） |
| `components/DuePicker.tsx` | 期限の欄のボタンと、カレンダーを出す位置の管理 |

- **計算は、画面から切り離す**：6週間分の日付を作る `monthGrid` は、画面と関係のない関数にして、単体でテストした（うるう日、年またぎ、1日が日曜の月）。画面の部品を作る前に、計算の間違いを見つけられる
- **日付は文字列のまま、計算は UTC で**：`'2026-10-15'` の形のまま扱い、日付の計算だけ `Date.UTC` を使う。`new Date('2026-10-15')` のようなローカル時間の計算だと、時差でずれることがある
- **6週間分（42日）**：月が変わっても、高さが変わらない。その月の1日が何曜日かで、前の月の日付が何日ぶん入るかを決める
- **今回のバグ：曜日の色**：日付1つずつに「日曜は赤・土曜は青」を付けるとき、**通し番号（0〜41）**で判断していたので、1行目しか色が付かなかった。正しくは、**列の位置（`i % 7`）**。見た目の確認で見つかった。**テストが、曜日の見出しだけを調べていて、日付を調べていなかった**のが原因。直したあと、全ての週を調べるテストを足した
- **カレンダーが見切れた**：カレンダーを、列やモーダルの中に出していたので、その枠（`overflow`）に切り取られた。
  - 対策：`createPortal` で、`body` の直下に出す。位置は `position: fixed`（画面に固定）で、欄の位置（`getBoundingClientRect`）から計算する
  - 欄のすぐ下が基本。下に入らず、上のほうが広いときだけ、上に出す。どちらにも入らないときは、画面の中に収まる位置にずらす。右端からも、はみ出さない
  - 画面の大きさやスクロールが変わったら、位置を決め直す（`resize`、`scroll` のイベント）
- **ポータルとイベント**：ポータルで別の場所に出した部品でも、React のイベントは、元の親に伝わる。そのため、窓の外を押したか調べるときは、`e.target === e.currentTarget`（窓そのものを押したか）で見分けている。一方、`document` に付けた「外を押したか」の判定は、画面の部品の親子ではなく、実際の場所（DOM）で見るので、カレンダーの中かどうかを、別に調べる必要がある
- **Esc の順番**：カレンダーが開いているときの Esc は、カレンダーだけを閉じる。カレンダーは、`document` で、**キャプチャ**（イベントが降りていく途中）で先に受け取り、`stopPropagation()` で、それより先に伝えない。次の Esc で、モーダルが閉じる
- **フォーカスを奪わない**：カード追加の入力欄は、フォーカスが外に出ると、確定または閉じる。カレンダーを触っただけで閉じないよう、`onMouseDown` で `preventDefault()` して、入力欄からフォーカスを動かさない
- **テストで、画面の大きさを決め打ちにする**：テスト環境（jsdom）には、画面の大きさがない。`getBoundingClientRect` と `window.innerHeight` を、テストの中で決めた値に差し替えて、「下／上／画面に収まる位置／右端」を調べた

### やってみよう
1. カードを押して、期限の欄を押す → カレンダーが開く。日付を押すと、すぐに選ばれて閉じる
2. ＜＞で月を移る。曜日と日付の色（日曜は赤、土曜は青）を、全ての週で見る
3. 「期限を外す」で、期限がなくなる
4. カレンダーを開いたまま Esc → カレンダーだけが閉じる。もう一度 Esc → モーダルが閉じる
5. ブラウザの画面を小さくして、画面の下のほうで開く → 上に出る／収まる位置にずれる

## 9. カードの削除（確認メッセージ付き）
編集モーダルの左下に「削除」ボタンを置いた。押すと、**モーダルの中**で「本当に削除しますか？」と確認が出る。「削除する」を押すと、`DELETE /api/cards/{id}` を送り、ボードを取り直して、モーダルを閉じる。

| ファイル | 変更 |
|---|---|
| `api/client.ts` | `deleteCard(id)` を追加。`request()` が、204 のときは JSON を読まずに終わるようにした |
| `components/CardModal.tsx` | 「削除」ボタン、削除の確認、削除中の動きを追加 |

- **204 は、JSONを読めない**：今までの `request()` は、成功すると必ず `response.json()` を呼んでいた。204 No Content は中身が空なので、そのまま読むと失敗する。そこで、`status === 204` のときは、読まずに終わるようにした（バックエンドの学習ノート、13章と対応）
- **確認は、状態（state）で切り替える**：`confirmingDelete` という true / false を持つ。true のときは、いつものボタン（削除・キャンセル・保存）の代わりに、確認の枠（「削除する」「キャンセル」）を出す。`window.confirm`（ブラウザ標準の確認）ではなく、画面の中に出すので、見た目をそろえられて、テストもしやすい
- **確認の「キャンセル」にフォーカス**：確認が出たとき、まず「キャンセル」にフォーカスを置く（`autoFocus`）。Enter を押しても、消えない。取り返しのつかない操作は、安全なほうを初期にする
- **Esc の意味が、場面で変わる**：確認が出ている間の Esc は、確認だけを閉じて、編集に戻る。通常の Esc は、モーダルを閉じる。窓の外を押したときも、同じ。この判断を `dismiss` という1つの関数にまとめた
- **削除中は、閉じない**：保存のときと同じ作り。通信中は `saving` を true にして、ボタンを押せなくする。`savingRef` で、二重に送るのも防ぐ。Esc や窓の外でも、閉じない
- **失敗したら、確認を出したまま**：404 などで失敗したら、エラーを表示して、やり直せるようにした
- **useCallback と依存の配列**：`dismiss` は、`confirmingDelete` の値によって動きが変わる。そのため `useCallback` の依存に `confirmingDelete` を入れた。最初は、ref（`useRef`）に値を写して避けたが、lint に「描画中に ref を書き換えている」と注意された。**値は、state をそのまま使うのが素直**
- テスト：確認が出る（まだ削除されない）／キャンセルで編集に戻る／確認中の Esc は確認だけ閉じる／「削除する」で DELETE が送られ、カードがボードから消える／失敗したらエラーを出す／通信中はボタンが押せず Esc でも閉じない／`deleteCard` が 204 でも失敗しない

### やってみよう
1. DB・バックエンド・画面を起動して、カードを1枚追加する
2. そのカードを押し、「削除」を押す → 確認が出る。「キャンセル」で、編集に戻る
3. もう一度「削除」→「削除する」。カードがボードから消える
4. 確認を出して Esc → 確認だけが閉じる。もう一度 Esc → モーダルが閉じる
5. （発展）バックエンドを止めてから「削除する」を押し、エラーが出ることを見る

## 10. カードのドラッグ＆ドロップ（dnd-kit）
カードをつかんで、別の列へも、同じ列の中でも動かせるようにした。動かした位置は、バックエンドの `PUT /api/cards/{id}/move`（バックエンドの学習ノート、14章）で保存する。

| ファイル | 役割 |
|---|---|
| `components/Board.tsx` | `DndContext`（ドラッグ＆ドロップの全体を管理する入れ物）。つかむ・動かす・置くの処理、先に画面へ反映する仕組み、保存の失敗の扱い |
| `components/BoardColumn.tsx` | 列。`SortableContext`（この列のカードは、縦に並べ替えられる）と、`useDroppable`（列全体が、カードを落とせる場所） |
| `components/CardItem.tsx` | カード。`useSortable`（このカードは、つかめて、並べ替えられる）。見た目は `CardFace` に分けた |
| `lib/moveCard.ts` | 動かした結果の計算（画面を使わない関数） |
| `lib/dragIds.ts` | `card-1`、`column-1` のような目印 |

### dnd-kit の部品
- **`DndContext`**：全体を包む。ここに、「つかんだ」「別の場所の上に来た」「置いた」「取り消した」の処理（`onDragStart` / `onDragOver` / `onDragEnd` / `onDragCancel`）を渡す
- **`useSortable`**：カードに付ける。つかむ操作（`listeners`）と、動いている間の見た目の位置（`transform`）をくれる
- **`useDroppable`**：列に付ける。カードが1枚もない列にも、落とせるようにする
- **`DragOverlay`**：つかんで動かしているカードを、マウスについてくる形で描く。元の場所のカードは、半透明（`opacity-40`）で残す
- **センサー**：マウス（`PointerSensor`）とキーボード（`KeyboardSensor`）。「何を、つかむ操作とみなすか」を決める部品

### 学んだポイント
- **「押す」と「つかむ」の区別**：カードを押すとモーダルが開く。動かさずに離せば「押した」、**5px 動いたら「つかんだ」**（`activationConstraint: { distance: 5 }`）。これがないと、ちょっと動いただけで、モーダルが開かなくなる。それでも、ドラッグの直後に「押した」と受け取られないよう、直後の100ミリ秒は、モーダルを開かない（`justDraggedRef`）
- **つかむ口は、`li` ではなく、中の `button` に付ける**：`listeners` と `attributes` を `li` に付けると、`li` の役割（リストの項目）が変わってしまう。ボタンに付ければ、見出しの読み上げも、今までのテストも、そのまま
- **カードのIDと列のIDは、同じ数字になる**（どちらも 1 から）。dnd-kit は「どれの上にあるか」をIDで教えるので、そのままでは区別できない。そこで、`card-1` と `column-1` のように、前に文字を付けた（`lib/dragIds.ts`）
- **先に画面へ反映し（楽観的更新）、あとで保存する**：置いたとき、保存の結果を待つと、カードが一瞬、元の場所に戻って見える。そこで、先に新しい並びを見せて（`pending`）、保存し、成功したらボードを取り直す。**失敗したら、元の並びに戻して、エラーを出す**
  - `pending` は、「どの `cards` をもとにしたか」（`base`）を一緒に持つ。取り直した新しい `cards` が届くと、`base` と違うので、自動で使われなくなる（消す処理を書かなくてよい）
- **別の列の上に来たら、その場で入れて見せる**：`onDragOver` で、別の列の上に来た時点で、カードをその列に入れる。そうすると、その列のカードが、場所をあけてくれる。同じ列の中の入れ替えは、`SortableContext` が自動でやる
- **列の外で離しても、いちばん近い列に入る**：位置の判定に使っている `closestCorners` は、「いちばん近いもの」を必ず選ぶ。そのため、列と列のすき間や余白で離しても、「どこの上でもない」状態（`over` が `null`）にはならず、近い列に入る。Trello と同じ動きで、列の間が狭くても使いやすいので、これを仕様にした（UC-2）。最初は「列の外で離すと元に戻る」と思っていたが、**実際にブラウザで動かして、違うと気づいた**。キーボードのテストでは、列の外へ出せないので、見つけられなかった
- **元に戻したいときは Esc**：つかんでいる間に Esc を押すと、取り消せる（`onDragCancel` で `pending` を消す）。dnd-kit のマウス用の部品は、ドラッグ中の Esc を、最初から見張っている。**置いたあとは、Esc では戻らない**（もう保存したため）
- **画面とサーバーで、同じ計算をしている**：`lib/moveCard.ts` は、バックエンドの `moveCard` と同じ考え方（動かすカードを抜く → 差し込む → 連番を振る）。画面の予想と、サーバーの結果が、ずれにくい
- **絞り込み中は、動かせない**：検索で絞り込むと、画面には列の一部のカードしか出ない。「上から何番目に置いたか」が、列全体では分からなくなる。そこで、絞り込み中はつかめないようにして（`disabled`）、ヘッダーの下に、お知らせを出した。つかめるように見えないよう、カーソルの形も変える
- **キーボードでも動かせる**：スペースでつかむ → 矢印で動かす → スペースで置く。Esc で取り消し。**Enter は、モーダルを開くために空けておいた**（Enter でもつかめると、「開く」と「つかむ」がぶつかる）。読み上げの案内の文は、日本語にした（`accessibility`）
- **テスト**：`lib/moveCard.test.ts` で、計算を単体で調べる（別の列／同じ列／空の列／範囲外／負の position）。画面のテストは、jsdom には画面上の位置がないので、`getBoundingClientRect` を差し替えて、「列は横に、カードは縦に並んでいる」ことにし、**キーボードで動かして**、送られた内容と、並びを調べた
  - マウスでのドラッグは、jsdom では再現しにくいので、ブラウザで確認する

### やってみよう
1. DB・バックエンド・画面を起動する
2. カードを、マウスでつかんで、同じ列の中で動かす → 画面を読み込み直しても、位置が残る
3. 別の列へ動かす。カードがない列にも、動かす
4. 列のすき間や余白で離す → いちばん近い列に入る。つかんでいる間に Esc を押す → 元の位置に戻る
5. カードを動かさずに、短く押す → モーダルが開く
6. カードにフォーカスして、スペース → 矢印 → スペースで、キーボードでも動かす
7. キーワードで検索する → お知らせが出て、カードが動かせない。「クリア」で、動かせるようになる
8. （発展）バックエンドを止めて、カードを動かす → エラーが出て、元の並びに戻る

## 11. 「期限順」ボタン
各列の上部に「期限順」ボタンを置いた。押すと、その列のカードが、期限の早い順に並び直る。バックエンドの `POST /api/columns/{id}/sort-by-due`（バックエンドの学習ノート、15章）を呼ぶ。

| ファイル | 変更 |
|---|---|
| `api/client.ts` | `sortColumnByDue(columnId)` を追加（POST、並び直したカードが返る） |
| `components/BoardColumn.tsx` | 列の上部に「期限順」ボタン。通信中は押せない（`disabled`） |
| `components/Board.tsx` | `handleSortByDue`：APIを呼ぶ → 成功したらボードを取り直す → 失敗したらエラーを表示 |

- **並べ替えは、画面ではなく、サーバーがやる**：画面で並べ替えるだけだと、開き直したら元に戻ってしまう。「並べた順が保存される」ので、サーバーに頼んで、`position` を書き換えてもらう。画面は、「頼む」「取り直して表示する」だけ
- **先に画面を変えない（ドラッグとの違い）**：ドラッグ＆ドロップは、置いた瞬間に動かないと不自然なので、先に画面へ反映した（楽観的更新）。「期限順」は、ボタンを押してから結果が出るまで、一瞬待つのが自然で、サーバーの結果をそのまま見せたほうが、間違いがない。そこで、取り直すだけにした
- **確認のメッセージは出さない**：削除と違って、手でまた並べ直せる。操作の回数を減らしたい（非機能要件）ので、押したらすぐ並び直す
- **絞り込み中でも押せる**：ドラッグが絞り込み中に無効なのは、画面に出ているカードが「列の一部」で、置いた位置が列全体の何番目か分からないから。「期限順」は、サーバーが列全体を並べ直すので、画面が位置を決める必要がない。取り直すときも、同じ絞り込みの条件で取るので、絞り込んだ結果が、期限順で出る
- **通信中は、全部の列のボタンを押せなくする**：`sortingColumnId` に、並べ直している列を持つ。別の列のボタンも押せなくすることで、2つの並べ替えが同時に走るのを防ぐ。`finally` で、成功しても失敗しても、必ず解除する
- **ボタンの名前**：画面には「期限順」とだけ出るが、読み上げ用の名前（`aria-label`）は「ToDoを期限順に並べ替え」にした。3つの列に同じ名前のボタンが並ぶので、どの列か分かるようにするため（「＋」ボタンが「ToDoにカードを追加」なのと同じ考え方）
- テスト `CardSort.test.tsx`：各列にボタンがある／押した列だけが期限順になり、期限なしが末尾／確認が出ない／失敗したらエラーが出て並びはそのまま／通信中は押せない／絞り込み中でも押せて、絞り込んだ結果が出る。`client.test.ts` に、POST の呼び出しと接続エラーを追加

### やってみよう
1. 期限の違うカードと、期限のないカードを、1つの列に数枚入れる（期限は、モーダルで設定する）
2. その列の「期限順」を押す → 期限の早い順に並び、期限なしが末尾になる。画面を読み込み直しても、同じ順
3. 同じ期限のカードを2枚入れて「期限順」を押す → 2枚の順番は変わらない
4. 並び直したあとで、ドラッグ＆ドロップで動かす → 動かせる
5. 並び直したあとで、カードを追加する → 列の一番上に入る
6. キーワードで検索してから「期限順」を押す → 絞り込んだ結果が、期限順で出る。「クリア」で全部を見ると、列全体も期限順になっている

## 12. バックアップ（保存と読み込み）
画面の右上に、「バックアップ」と「読み込み」のボタンを置いた。バックエンドの `GET /api/backup` と `POST /api/backup/restore`（バックエンドの学習ノート、16章）を使う。

| ファイル | 役割 |
|---|---|
| `api/client.ts` | `fetchBackup()`（GET）、`restoreBackup(file)`（POST）。400 のときの文を、呼ぶ側で決められるようにした |
| `lib/backup.ts` | 画面を使わない関数：`backupFileName`（日時付きのファイル名）、`parseBackupText`（ファイルの軽い検査）、`saveJsonFile`（ダウンロードで保存） |
| `components/ConfirmDialog.tsx` | 確認・お知らせの小さな窓（メッセージとボタン）。Esc・窓の外で閉じる。通信中は閉じない |
| `components/BackupControls.tsx` | 2つのボタンと、ファイル選び、窓の出し分け、保存と読み込みの流れ |

### 流れ
- **保存**：「バックアップ」→ `fetchBackup()` でJSONを受け取る → `Blob`（ファイルの中身を表すもの）にする → 見えない `<a download>` リンクを作って `click()` → ブラウザが、ファイルとして保存する → リンクを消す
- **読み込み**：「読み込み」→ 隠した `<input type="file">` を `click()` で開く → 選んだファイルを `file.text()` で読む → `parseBackupText` で軽く調べる
  - 読めない（JSONでない／`app` が `taskboard` でない／`columns` がない）：お知らせ「このファイルは読み込めません。」（閉じる）
  - 読める：確認「現在のデータは、すべて置き換わります。よろしいですか？」（キャンセル／読み込む）→ 「読み込む」で `restoreBackup` → 成功したら窓を閉じ、ボードを取り直し、「バックアップを読み込みました。」を出す

### 学んだポイント
- **ファイル選びのボタンは、隠して、別のボタンから開く**：`<input type="file">` は、見た目を変えにくい。そこで、`input` は `hidden` にして、見た目を整えた「読み込み」ボタンから `inputRef.current.click()` で開く。`aria-label` を付けて、テストと読み上げで見つけられるようにした
- **選んだあと、`input.value = ''` にする**：そのままだと、同じファイルをもう一度選んでも、「変わっていない」とされて `onChange` が動かない。読み込みをやり直すときに困るので、選んだ直後に空にする
- **検査は2段構え**：画面の `parseBackupText` は、「このアプリのバックアップらしいか」だけを軽く調べる（確認を出す前の関門）。色や日付の細かい検査は、サーバーが行う（正しいのはサーバー）。サーバーが 400 で断ったときも、同じ「このファイルは読み込めません。」を出す。画面とサーバーの両方で、読めないファイルが、データを壊さないようにしている
- **画面は、ファイルの中身を作り変えない**：読んだJSONを、そのままサーバーに送る。画面が中身の細かい形を知らなくてよい（`columns: unknown[]`）。形式が変わっても、画面を直さなくてよい
- **破壊的な操作は、確認の窓の最初のフォーカスを、安全なほうに置く**：確認では「キャンセル」に `autoFocus`。Enter を押しても、読み込まれない（削除の確認と同じ考え方）。確認のボタンは、赤（`danger`）にして、注意を引く
- **通信中は、窓を閉じられない**：`busy` の間は、ボタンが押せず、Esc・窓の外でも閉じない。`busyRef` で、二重に押されるのも防ぐ（保存・削除と同じ作り）
- **`File.text()`**：ファイルの中身を、文字として読む（`Promise` を返す）。失敗したときに備えて `.catch(() => '')` で空にし、読めないファイルとして扱った
- **ダウンロードのテスト**：テスト環境（jsdom）には、ダウンロードがない。`URL.createObjectURL` を差し替えて、渡された `Blob` の中身を調べ、リンクの `click()` を差し替えて、`download`（ファイル名）を調べた
- **公開リポジトリへの注意**：バックアップのファイルには、個人の予定が入る。うっかりコミットしないよう、`.gitignore` に `taskboard-backup-*.json` を足した
- テスト：`Backup.test.tsx`（保存／保存の失敗／読み込み：確認 → 送信 → 取り直し／キャンセル／Esc／読めないファイル／別アプリのJSON／サーバーが400／通信中は閉じない）、`lib/backup.test.ts`、`client.test.ts`

### やってみよう
1. DB・バックエンド・画面を起動する。「バックアップ」を押して、ダウンロードされたファイルを、メモ帳などで開く（列とカードが、入れ子のJSONになっている）
2. カードを何枚か消す、または動かす
3. 「読み込み」→ さっきのファイルを選ぶ → 確認で「キャンセル」→ 何も変わらない
4. もう一度「読み込み」→ 同じファイルを選ぶ → 「読み込む」→ 元のカードと並びに戻る。画面を開き直しても、同じ
5. 適当なテキストファイルを選ぶ → 「このファイルは読み込めません。」と出て、データは変わらない
6. （発展）ファイルの `"app"` を書き換えて読み込む → 読み込めない

## 13. 背景（選ぶ・表示する）
ヘッダーに「背景」ボタンを置いた。無地・青空・夕焼け・星空・自動（時間帯）から選ぶと、画面いっぱいの背景が切り替わる。バックエンドの `GET/PUT /api/settings`（バックエンドの学習ノート、17章）に保存するので、開き直しても残る。

| ファイル | 役割 |
|---|---|
| `lib/background.ts` | 画面を使わない関数：選択肢の一覧、自動の判定（`sceneAt`）、選んだ背景から「いま出す場面」を決める（`resolveScene`）、列の色合い（`toneOf`） |
| `hooks/useSettings.ts` | 設定の取得と保存。自動のときの時刻の見直し |
| `hooks/usePopover.ts` | ボタンの下に開く小さな窓の、位置決めと「外を押したら閉じる」。`DuePicker` から切り出して、共用した |
| `components/BackgroundLayer.tsx` | 画面いっぱいに固定した背景の層 |
| `components/BackgroundPicker.tsx` | 「背景」ボタンと、見本つきの選択の窓 |
| `index.css` | 背景の見た目（標準の画像 ＋ 代わりのグラデーション） |
| `public/backgrounds/` | 標準の画像3枚と `CREDITS.md` |

### 学んだポイント
- **「選んだ背景（5種類）」と「いま出す場面（4種類）」は別もの**：「自動」は、場面ではなく、「時刻で場面を決める」という選択。`resolveScene(背景, 時刻)` が、自動のときだけ時刻を見て、青空・夕焼け・星空のどれかにする。選んだ背景は設定として保存し、場面は、その都度、計算する（保存しない）
- **時刻の判定は、画面から切り離して、境目をテストする**：`sceneAt` は、`Date` を受け取るだけの関数。4:59 / 5:00 / 15:59 / 16:00 / 17:59 / 18:00 のような**境目**を、単体テストで確かめた（`<` と `<=` の間違いは、境目でしか見つからない）
- **開いたままでも切り替わる**：自動のときだけ、30秒ごとに時刻を見直す（`setInterval`）。自動でなくなったら、タイマーを止める（`useEffect` の戻り値で `clearInterval`）。テストでは、`setInterval` を差し替えて、30秒後の関数を取り出し、偽の時刻にして呼んだ
- **先に画面を変えて、保存し、失敗したら戻す**：背景を選んだ瞬間に切り替える（ドラッグ＆ドロップと同じ考え方）。保存に失敗したら、前の背景に戻して、エラーを出す
- **画面いっぱいの背景は、`fixed inset-0 -z-10` の層にする**：`fixed` はスクロールしても動かない。`-z-10`（奥行きがマイナス）で、ほかの部品の後ろに回す。そのため、画面全体を包む枠には、背景色を付けなかった（付けると、層が隠れる）。無地のときの色は、`body` に付けた
- **標準の画像が読み込めないときの代わり**：CSS の `background` は、複数の層を重ねられる。一番上に画像、その下にグラデーションを書くと、画像が読み込めなかったとき、下のグラデーションが見える（試作から引き継いだ）
- **同じCSSを、背景と見本で使い回す**：`.bg-scene-sky` などのクラスを、画面いっぱいの層にも、選択の窓の小さな四角（見本）にも付ける。見本と本番の見た目がずれない
- **文字の読みやすさは、「列」と「カード」で守る**：背景があるとき、列を75%の不透明にして、背景を少し透かす（`bg-[#e9edf5]/75`）。カードは不透明のまま。星空は、背景が暗いので、列を暗い紺色にして、見出し・「＋」・「カードがありません」を明るい文字にする。`BoardColumn` に `tone`（`plain` / `light` / `dark`）を渡して、色の組み合わせをまとめた
- **共通の部品に切り出す（リファクタリング）**：「ボタンの下に開く窓」は、期限のカレンダー（`DuePicker`）と、背景の選択で、同じ動き（位置決め、画面からはみ出さない、外を押したら閉じる）。2回目に作るときに、`usePopover` という hook に切り出して、`DuePicker` も書き換えた。**既存のテストが通ったこと**で、動きを変えていないと確かめられた
- **想定外の返事は、無視する**：設定の返事の `background` が、5つのどれでもなければ、取り込まない（`isBackground`）。形の違う返事でも、ボードは表示される
- **バックアップを読み込んだら、背景も取り直す**：バックアップには背景の設定が入っているので、読み込んだあとは `settings.reload()` で取り直す
- テスト：`lib/background.test.ts`（境目）、`Background.test.tsx`（保存された背景の表示／選択肢と選択状態／選ぶと切り替わって保存／無地は層がない／外・Esc／失敗で元に戻る／列の色合い／自動の時刻と切り替わり／形の違う返事）、`client.test.ts`、`Backup.test.tsx`（読み込み後に背景を取り直す）

### やってみよう
1. 「背景」を押して、5つの選択肢と見本を見る。青空・夕焼け・星空を順に選ぶ
2. 星空を選ぶ → 列が暗い紺色になり、見出しが明るくなる。カードの文字は読めるか
3. 画面を読み込み直しても、選んだ背景のままか
4. 「自動（時間帯）」を選ぶ → いまの時刻の背景になる（5〜16時は青空、16〜18時は夕焼け、18時〜翌5時は星空）
5. 「無地」を選ぶ → 背景がなくなり、今までの見た目に戻る
6. 「バックアップ」で保存 → 背景を変える → 「読み込み」で戻す → 背景も、保存したときのものに戻る
7. 画面を縦にスクロールしても、背景が動かないか

## 15. 自分の画像を背景にする（縮小して送る）
「背景」の窓の、青空・夕焼け・星空の行に、「画像を選ぶ」と「元に戻す」を足した。バックエンドの `/api/background-images`（バックエンドの学習ノート、18章）を使う。

| ファイル | 役割 |
|---|---|
| `lib/image.ts` | 画像の種類（JPEG・PNG・WebP）の判定、20MBの上限、縮小後の大きさ（`fitWidth`）、canvasでJPEGに縮小（`resizeToJpeg`） |
| `hooks/useBackgroundImages.ts` | 登録済みの画像を持つ。登録（検査 → 縮小 → 送信）と、削除 |
| `components/BackgroundPicker.tsx` | 各行の「画像を選ぶ」「元に戻す」。見本に自分の画像を出す。失敗のお知らせ |
| `components/BackgroundLayer.tsx` | 自分の画像があれば、それを画面いっぱいに出し、暗幕を重ねる |
| `api/client.ts` | `fetchBackgroundImages`、`uploadBackgroundImage`、`deleteBackgroundImage`、`backgroundImageUrl` |

### 流れ
「画像を選ぶ」→ 隠した `<input type="file">` が開く → 選んだファイルを検査（種類 → 大きさ）→ `resizeToJpeg` で縮小 → `PUT /api/background-images/{slot}` で送る → 成功したら、その背景に切り替える（`PUT /api/settings`）

### 学んだポイント
- **縮小は、画面（ブラウザ）でやる**：20MBの写真をそのまま送ると、通信もDBも重くなる。ブラウザの `canvas`（絵を描く場所）に、小さくして描き直し、JPEGとして取り出す。流れは、`createImageBitmap(file)`（ファイルを画像として読む）→ `canvas.width/height` に縮小後の大きさ → `drawImage` で描く → `canvas.toBlob(…, 'image/jpeg', 0.85)`（JPEGにして取り出す。0.85は画質）
- **縮小後の大きさの計算は、画面から切り離して、テストする**：`fitWidth(幅, 高さ)`。横が1920pxより大きいときだけ、比率を保って縮小する（小さい画像は、**拡大しない**。拡大すると、ぼやけるだけで、データも増える）。高さは四捨五入し、とても横長の画像でも、1px以上にする。canvas を使う `resizeToJpeg` 本体は、テスト環境（jsdom）では動かないので、テストでは差し替えて、**実際の縮小は、ブラウザで確かめた**
- **透明なPNGは、白で塗ってから描く**：JPEGには「透明」がない。そのまま変換すると、透明な部分が黒くなる。先に白で塗りつぶしてから、画像を描いた
- **検査の順番**：①種類（JPEG・PNG・WebP か）②大きさ（20MBを超えないか）③縮小できるか（壊れたファイルは、種類が画像でも、開けない）。どれも、サーバーに送る前に、画面で止める。**ちょうど20MBは通り、1バイトでも超えると大きすぎる**（境目をテスト）。サーバーも、JPEGの先頭の目印と5MBの上限を、もう一度検査する（画面を通さない送信にも備える）
- **`accept` は、あくまで親切**：`<input type="file" accept="image/jpeg,image/png,image/webp">` は、ファイル選びの窓で、画像だけを選びやすくする。でも、「すべてのファイル」に切り替えれば、ほかのファイルも選べる。だから、選んだ後の検査は、必ず必要。なお、テストの `userEvent.upload` は、`accept` に合わないファイルを、**黙って除く**。画像でないファイルのテストには、`applyAccept: false` が要る
- **`input.value = ''`**：選んだ直後に空にして、同じファイルをもう一度選んでも `onChange` が動くようにする（バックアップの読み込みと同じ）
- **ファイル選びの `input` は、窓の外に置く**：選択の窓（ポップオーバー）は、外を押すと閉じて、消える。窓の中に `input` を置くと、ファイルを選んだ結果を、受け取れなくなる。そこで、`input` は窓の外に置き、どの行の「画像を選ぶ」を押したかは、`useRef` に覚えておく。ファイルが選ばれたら、お知らせの窓が隠れないよう、先に選択の窓を閉じる
- **画像の URL に、登録日時を付ける**：`/api/background-images/sky?v=2026-10-16T…`。画像を置き換えると、日時が変わり、URL も変わる。ブラウザは、別の画像として取り直す（古い画像が残らない）。サーバーの ETag（バックエンドの学習ノート、18章）と合わせて、「変わっていなければ送り直さない、変わったらすぐ新しい画像」になる
- **画像のURLは、CSSの `background-image` に入れる**：自分の画像は、`style={{ backgroundImage: 'linear-gradient(暗幕), url("…")' }}` と書く。**暗幕は、画像の上に重ねる半透明の黒のグラデーション**（`rgba(0,0,0,0.1)`＝黒10%）。標準の画像には重ねない（仕様）。最初は20%にしたが、実際の写真で見て、「10%のほうが写真がきれいに見える」と決めた。濃さは `BackgroundLayer.tsx` の1か所なので、見ながら調整できる
- **「自分の画像」を優先するかどうかは、いまの場面で決める**：`isUserImageSlot(場面)` が真で、その場面に登録があれば、自分の画像。自動のときは、時刻で決まった場面（青空・夕焼け・星空）で調べるので、**自動でも、その時間帯の登録画像が使われる**。無地と自動の行に「画像を選ぶ」がないのは、割り当て先が、青空・夕焼け・星空の3つだけだから
- **登録できたら、その背景に切り替える**：「画像を選んだのに、画面が変わらない」を避けるため。登録の成功のあとに、`setBackground(slot)` を呼ぶ
- **「元に戻す」は、確認なし**：元のファイルは、自分のPCにあって、登録し直せる（色の変更と同じ考え方。仕様 UC-12）。削除とバックアップの読み込みは、取り返しがつかないので、確認を出す
- **返事の形が違っても、画面は動く**：一覧の返事が配列でなかったり、知らない割り当て先が混じったりしても、無視する（標準の画像のまま）
- **サーバーが「大きすぎる」と断ったとき（413）も、同じ文を出す**：サーバーは、5MBを超える本文を、`413`（Content Too Large）で断る（バックエンド 05 の 18 章）。画面は縮小してから送るので、ほぼ起きないが、起きたときに「サーバーからエラーが返りました（413）」では分かりにくい。`request` の引数 `rejectedMessage`（元の名前は `badRequestMessage`）を、`400` と `413` の両方に使うようにして、「画像を登録できませんでした。別の画像を選んでください。」を出す。**専用の文を決めていない通信（削除など）の `413` は、これまでどおり、番号つきの一般的なエラー**にした（`rejectedMessage` があるときだけ、`413` を特別扱いする）
- テスト：`lib/image.test.ts`（種類・20MBの境目・縮小サイズ）、`BackgroundImage.test.tsx`（登録済みの画像が優先される／暗幕／標準のまま／行ごとのボタン／見本／登録して切り替わる／画像でない／20MBの境目／開けない画像／サーバーが断る／元に戻す／自動／返事の形が違う）、`client.test.ts`

### やってみよう
1. 「背景」→ 青空の行の「画像を選ぶ」→ 大きな写真を選ぶ。青空の背景に、その写真が出て、暗くなりすぎず、文字が読めるか
2. 画面を読み込み直しても、写真が残っているか。ブラウザの開発者ツールの「ネットワーク」で、画像の大きさが、数百KB程度か（縮小されている）
3. テキストファイル（や、PDF）を選ぶ → 「このファイルは読み込めません。…」と出るか。ファイル選びの窓で、「すべてのファイル」に切り替えて選ぶ
4. 夕焼けと星空にも、別の画像を登録する。「自動」にして、時間帯で切り替わるか（時刻を待たなくても、青空・夕焼け・星空を順に選んで確かめる）
5. 青空の行の「元に戻す」→ 標準の青空の画像に戻る。夕焼け・星空の画像は残っているか
6. 「バックアップ」で保存 → 「読み込み」で戻す → 登録した画像が消えずに残っているか（バックアップには、画像は入らない）

## 16. モーダルを `<dialog>` にする（品質チェック F1）

### 何が問題だったか
編集の窓は、`<div>` で作り、`aria-modal="true"` と書いていた。でも、これは「読み上げソフトへの申告」で、**動きは何も変えない**。実際に試すと、次のことが起きた。
- 窓を閉じたあと、フォーカス（キーボードの操作を受け取る場所）が、押したカードに戻らず、Tab を押すと、ブラウザの部品（タブ検索）に飛んだ
- Tab で、窓の外に出られる（窓の後ろの画面が、操作できる状態のまま）

### 直し方：HTML 標準の `<dialog>`
`<dialog>` 要素を、JavaScript の `showModal()` で開くと、ブラウザが自動で、次のことをしてくれる。
- フォーカスを、窓の中に閉じ込める（Tab が、窓の中を回る）
- 後ろの画面を、操作できない状態（inert）にする
- 暗い背景（`::backdrop`）を出す。Tailwind では `backdrop:bg-black/40`
- Esc で、`cancel` イベントが飛ぶ

自前で、フォーカスの閉じ込めを書くより、**標準の部品を使う**ほうが、短くて、バグが少ない。

### 関係するファイル
| ファイル | 役割 |
|---|---|
| `components/ModalDialog.tsx` | `<dialog>` を開き、閉じるときにフォーカスを戻す、共通の部品 |
| `components/CardModal.tsx`、`ConfirmDialog.tsx` | 中身だけを書く（`ModalDialog` で包む） |
| `components/DuePicker.tsx` | カレンダーを、窓の中に出す |
| `test-setup.ts` | テスト環境（jsdom）に、`showModal` の代わりを用意する |

### 学んだポイント
- **開く前にフォーカスがあった場所は、描く前に覚える**：`useState(() => document.activeElement)`。窓の中の `autoFocus` が、先にフォーカスを奪うので、あとからでは、元の場所が分からない。閉じるときに、その場所に `focus()` する
- **Esc は、「そのまま閉じさせない」**：`onCancel` で `preventDefault()` して、自分の `onDismiss` に任せる。通信中は閉じない、削除の確認だけを閉じる、など、閉じるかどうかを、こちらで決めるため
- **ブラウザが勝手に閉じることがある**：Esc を続けて押すと、止めても閉じることがある。そのために、`onClose` で、閉じていたら開き直す
- **窓の外（暗い背景）を押したか**：背景を押すと、`<dialog>` 自身が押されたことになる（`e.target === e.currentTarget`）。中身は、内側の `<div>` が覆っているので、窓の中を押しても、これにならない
- **モーダルが開いている間、窓の外は、操作できない**：期限のカレンダーは、列やモーダルの枠で切り取られないように、画面の末尾（`document.body`）に出していた。でも、それだと、モーダルの中では、カレンダーを押せなくなる。そこで、`closest('dialog')` で、窓の中を探し、あれば、その中に出すようにした
- **カレンダーの Esc で、窓まで閉じない**：カレンダーの Esc の処理に、`preventDefault()` を足した（ブラウザは、止められていない Esc を、窓を閉じる合図にする）
- **テスト環境（jsdom）には、`showModal` がない**：`test-setup.ts` で、開く・閉じる・Esc を、最小限まねた。ただし、**Tab の閉じ込めと、後ろの画面を操作できなくすること（inert）は、まねられない。実際のブラウザで、確かめた**
- テスト（`CardModal.test.tsx`）：`<dialog>` で開く／閉じるとフォーカスが戻る／窓の中を押しても閉じない／強制的に閉じられたら開き直す／カレンダーが窓の中に出て、Esc ではカレンダーだけが閉じる

### やってみよう
1. カードを Tab で選んで Enter で窓を開き、Tab を何度も押す。フォーカスが、窓の中を回るか（後ろのカードに、枠線が出ないか）
2. Esc で閉じて、もう一度 Tab を押す。開いたカードの、次のカードに移るか
3. ブラウザの開発者ツール（F12）の「要素」で、窓を探す。`<dialog open>` になっているか。窓が開いている間、後ろの `<div id="root">` が操作できない（inert）扱いになっているか

## 17. ドロップ先の青い線（設計書に実装を合わせる）

### 何をしたか
画面設計書には、最初から、「ドロップ先は、青い線で示す」と書いてあった。でも、実装は、カードを動かすと、**他のカードが動いて、空きができる**だけで、青い線はなかった。品質チェック（D1）で、「青い線があったほうが分かりやすい」と決めて、**実装を、設計書に合わせた**。

### 仕組み
dnd-kit の `useSortable` は、ドラッグ中のカードに、`isDragging`（いま、つかまれているか）を教えてくれる。つかまれているカードは、元の場所に**半透明で残り**、他のカードが動くと、**そのカードが、いまの落とし先の場所に、一緒に動いてくる**。そこで、**つかまれているカードの、すぐ上のすき間に、青い線を出す**ようにした。

| もの | 内容 |
|---|---|
| `components/CardItem.tsx` | `isDragging` のときだけ、青い線の `<span>` を出す |
| 線の位置 | カードの上端から、すき間の真ん中（`-top-[5.5px]`）。カードの間のすき間は 8px（`gap-2`）なので、その真ん中 |
| `relative` と `absolute` | カード（`<li>`）を基準にして、線を重ねる。線は、場所を取らない（レイアウトが動かない） |
| `pointer-events-none` | 線は、マウスの操作を受けない（下のカードを、つかむ・押すのを邪魔しない） |
| `aria-hidden="true"` | 読み上げソフトには、読ませない（読み上げは、別に用意してある） |

### 学んだポイント
- **新しい部品を足さずに、今ある状態（`isDragging`）を使う**：ドラッグ中のカードの位置は、dnd-kit が、もう計算してくれている。それに、線を1本、足すだけで済んだ。「落とす場所」を、自分で計算する必要はない
- **見た目の調整は、先に試す**：まず、コミットせずに、起動中の画面に入れて、ユーザーに見てもらった（太さ、位置、半透明のカードを残すか）。「どれも OK」と決まってから、テストと文書を整えて、PR にした
- **見た目を、テストで確かめる工夫**：線に `data-testid="drop-indicator"` という目印を付けて、「つかんでいる間だけ、1本出る」「別の列に運べば、その列に移る」「置く・Esc で、消える」「絞り込み中は、出ない」を、テストした
- **間違えやすい操作**：キーボードでは、**スペース（つかむ）→ 矢印（動かす）→ もう一度スペース（置く）**。矢印で動かしただけの間は、まだカードを持っているので、青い線が出ているのが正しい。置くと、線が消えて、カードに**フォーカス**（黒い枠線）が残る
- **半透明のカードと、青い線の、両方がよく見える**：背景の画像（星空など）を変えても、半透明のカードが見えるので、線が控えめでも、落とす場所が分かる

### やってみよう
1. カードをマウスでつかんで、同じ列の中で、ゆっくり動かす。青い線が、カードの間に出るか
