# 06 フロントエンド（画面）の仕組み

`frontend/` の中の、React + TypeScript の画面。**本番の画面**になる。
使い方は [frontend/README.md](../frontend/README.md)、技術の決定は [docs/tech-stack.md](../docs/tech-stack.md) を参照。

## 1. 道具の役割
| 道具 | 役割 | たとえ |
|---|---|---|
| Node.js | JavaScript を、ブラウザの外で動かす土台 | 厨房の電気・ガス |
| npm | 部品（ライブラリ）を入れたり、コマンドを実行したりする | 食材の仕入れ係 |
| Vite | 開発用のサーバーと、本番用のビルドをする | 試食用の仮設キッチン |
| React | 画面を「部品（コンポーネント）」の組み合わせで作る | 料理の型 |
| TypeScript | JavaScript に「型」を足す。書き間違いを、実行前に見つける | レシピの誤字チェック |
| Tailwind CSS | `class="p-3 rounded-lg"` のように、短い指定で見た目を決める | 盛り付けの定型 |
| Vitest | 画面の部品が、思ったとおりに動くか、自動で確かめる | 味見の自動化 |

- `package.json`：使う部品の一覧と、コマンド（`npm run dev` など）が書いてある
- `package-lock.json`：実際に入った部品の、正確なバージョンの記録（コミットする）
- `node_modules/`：入れた部品の置き場。大きいので、コミットしない（`npm install` でいつでも再現できる）

## 2. 画面が、データを表示するまでの流れ
```
ブラウザ → (5173番) Vite → /api/... は、そのまま (8080番) バックエンドへ中継 → DB
```
1. 画面を開くと、`App` が `useBoard` を呼ぶ
2. `useBoard` が、`/api/columns`（列）と `/api/cards`（カード）を、同時に取りにいく
3. 結果を、`Board` → `BoardColumn` → `CardItem` の順に渡して、表示する

### なぜ、プロキシ（中継）を使うのか
- 画面（5173番）から、別の場所（8080番）に直接お願いすると、ブラウザが、安全のために止める（**CORS**）
- Vite に「`/api` は、8080番に回して」と設定（`vite.config.ts` の `proxy`）すると、ブラウザには「同じ場所とのやりとり」に見える
- そのため、バックエンドに、CORS の設定を足さずに済む
- バックエンドが止まっているときは、プロキシが `502` を返す。画面では「サーバーに接続できません」と表示する

## 3. フォルダの構成（`frontend/src/`）
| 場所 | 役割 |

| `api/client.ts` | APIを呼ぶ関数（取得 `fetchCards` など、追加 `createCard`、更新 `updateCard`、削除 `deleteCard`、移動 `moveCard`）。失敗したときの、分かりやすいエラーメッセージも作る |
| `hooks/useBoard.ts` | 列とカードを取得して、「読み込み中／エラー／成功」を管理する。`reload()` で取り直せる |
| `components/` | 画面の部品（SearchBar、Board、BoardColumn、CardItem、CardComposer、CardModal、ColorPicker、DuePicker、Calendar） |
| `lib/date.ts` | 期限の表示（「期限 10月15日」）と、期限切れの判定 |
| `lib/calendar.ts` | カレンダーの計算（6週間分の日付、前後の月） |
| `lib/moveCard.ts` | カードを動かした結果の計算（別の列へ、同じ列の中で。position の連番の振り直し）。画面を使わない「ただの関数」 |
| `lib/dragIds.ts` | ドラッグ＆ドロップで使う目印（`card-1`、`column-1`）。カードと列のIDが同じ数字でも、区別できるようにする |

## 4. 学んだポイント
- **状態（state）**：画面が覚えている値。値が変わると、React が画面を描き直す
- **日付は、文字列のまま比べる**：`'2026-10-12' < '2026-10-15'` のように、同じ形（YYYY-MM-DD）なら、そのまま日付の順に比べられる。`Date` を使うと、時差でずれることがある
- **古い結果で上書きしない**：検索を続けて行うと、前の問い合わせの結果が、あとから届くことがある。`useBoard` は、条件ごとに結果を持ち、今の条件のものだけを使う
- **テストの片付け**：Vitest では、テストのあとに、描いた画面を自分で片付ける（`cleanup`）。忘れると、前のテストの画面が残って、「同じ要素が複数ある」と失敗する
- **Tailwind の指定がぶつかる**：`bg-white` と `bg-[#4f7cff]` を同時に付けると、どちらが勝つかは、CSSの並び順で決まる。ボタンの文字が読めなくなったのは、これが原因だった。背景色は、1つだけ付ける
- **`strictPort`**：Vite は、5173番が使えないと、黙って別の番号で起動する。`strictPort: true` で、失敗させる。ただし、他のプロセスが全アドレス（`::`）で5173番を握っていると、気づけない。起動前の確認が必要（スキル `dev-port-conflict`）

## 5. やってみよう
1. `docker compose up -d` → `backend/` で `.\gradlew.bat bootRun` → `frontend/` で `npm run dev` の順に起動する
2. http://localhost:5173 を開き、3列にカードが並ぶのを確認する
3. 「キーワード」に「買」と入れて、「検索」を押す → カードが2枚に絞られる
4. 「期限（この日まで）」に日付を入れて検索する → 期限のないカードは、出てこない
5. バックエンドを止めて、画面を開き直す → エラーが表示される

## 6. カードの新規登録（画面から追加する）
流れ：列の「＋」→ `CardComposer`（入力欄）→ Enter → `createCard` が `POST /api/cards` → 成功したら `reload()` でボードを取り直す → 新しいカードが、列の一番上に出る。

- **GET と POST の違い**：取得（GET）は URL だけでよいが、追加（POST）は「送る中身」が要る。`fetch(url, { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify(入力) })` の形で送る
- **画面を直接書き換えず、取り直す**：追加したカードを自分で画面の一覧に足すこともできるが、並び順や ID の決定はバックエンドの役目。そのため、追加後はサーバーから取り直して、**サーバーの結果を正とする**
- **入力欄の外を押したとき**：`onBlur`（フォーカスが外れた）で、入力済みなら追加、空なら閉じる。ただし、色のボタンや期限欄を触っただけで閉じないよう、移動先が入力欄の中なら無視する（`relatedTarget`）。色ボタンは `onMouseDown` で `preventDefault()` して、フォーカスを奪わない
- **日本語入力の Enter**：漢字に変換して確定する Enter で、追加されてしまわないよう、`isComposing`（変換中）のときは無視する
- **二重送信の防止**：Enter とフォーカス外れが重なっても、2回送らないよう、`useRef` で「送信中」を覚えておく
- **失敗したとき**：400（タイトルが空・長すぎる）などは、エラーを表示して、入力欄と入力内容は残す

### やってみよう
1. 3つのサーバーを起動して、http://localhost:5173 を開く
2. ToDo 列の「＋」を押し、タイトルを入れて Enter → 一番上に出る。ページを再読み込みしても残る（DBに保存された）
3. 色の丸と期限の日付を選んで追加する → 背景色と「期限 ○月○日」が付く
4. Esc で取り消す／空のまま Enter を押す → 何も追加されずに閉じる

## 7. カードの編集（モーダル）
流れ：カードを押す → `Board` が「開いているカード」を覚える → `CardModal`（窓）が開く → 「保存」→ `updateCard` が `PUT /api/cards/{id}` → 成功したら `reload()` で取り直して、窓を閉じる。

| 部品 | 役割 |
|---|---|
| `CardItem` | カード全体を `button` にして、押せるようにした。説明文があれば、三本線の目印を出す |
| `Board` | どのカードを編集中かを、`useState` で持つ。`CardModal` を出し入れする |
| `CardModal` | 窓の本体。タイトル・説明文・色・期限を、窓の中だけの状態として持つ |
| `ColorPicker` | 色見本。追加の入力欄（`CardComposer`）と窓で、**同じ部品を使い回す** |

- **窓の中の入力は「下書き」**：入力した内容は、窓の中の状態にだけ入る。「保存」を押すまで、サーバーにも、ボードにも、届かない。だから、キャンセル・Esc・窓の外を押すだけで、変更を捨てられる
- **変更がなければ通信しない**：元のカードの内容と見比べて、同じなら、`PUT` を送らずに閉じる
- **空の値は「なし」**：説明文を消す、期限を外す、は `null` にして送る（バックエンドの仕様）。空白だけの説明文も `null` にそろえる
- **保存できない条件**：タイトルが空（空白だけ）のあいだは、「保存」ボタンを押せなくして、Enter でも送らない。保存中も二重に送らない（`useRef`）
- **失敗したとき**：窓を閉じずに、エラーを表示する。入力した内容は残るので、直してもう一度押せる
- **窓の外（暗い部分）を押して閉じる**：`onMouseDown` で、`e.target === e.currentTarget`（窓の外そのものを押した）ときだけ閉じる。窓の中の押下が、外に伝わって閉じてしまうのを防ぐ
- **Esc キー**：窓が開いている間だけ、`document` に `keydown` を付ける。`useEffect` の片付け（`return`）で、閉じたら外す
- **`key` を付ける理由**：`<CardModal key={editing.id}>` で、別のカードを開いたとき、前のカードの入力が残らないように、作り直す
- **テストは、画面全体を動かす**：`CardModal.test.tsx` は `App` を描いて、通信（`fetch`）だけをモックに替える。「押す→入力→保存→ボードに反映」を、ユーザーと同じ順番で確かめられる
- まだ作っていないもの：削除ボタン（14の回）。期限の自作カレンダーは、次の章（8章）で作った

### やってみよう
1. 3つのサーバーを起動して、http://localhost:5173 を開く
2. カードを押して、タイトル・説明文・色・期限を変えて保存する → ボードに反映され、再読み込みしても残る
3. 説明文を付けたカードに、三本線の目印が出ることを確かめる
4. 編集の途中で、キャンセル・Esc・窓の外を押す → 変更が捨てられる
5. タイトルを空にする → 「保存」が押せなくなる
6. バックエンドを止めて保存する → エラーが出て、窓が開いたままになる

## 8. 自作カレンダー（期限日）
期限の欄（`DuePicker`）を押すと、カレンダー（`Calendar`）が開く。編集のモーダルと、カード追加の入力欄の、両方で使う。

| ファイル | 役割 |
|---|---|
| `lib/calendar.ts` | カレンダーの計算（6週間分の日付、前の月・次の月）。画面を使わない「ただの関数」 |
| `components/Calendar.tsx` | カレンダーの見た目と操作（＜＞、曜日、日付、「期限を外す」） |
| `components/DuePicker.tsx` | 期限の欄のボタンと、カレンダーを出す位置の管理 |

- **計算は、画面から切り離す**：6週間分の日付を作る `monthGrid` は、画面と関係のない関数にして、単体でテストした（うるう日、年またぎ、1日が日曜の月）。画面の部品を作る前に、計算の間違いを見つけられる
- **日付は文字列のまま、計算は UTC で**：`'2026-10-15'` の形のまま扱い、日付の計算だけ `Date.UTC` を使う。`new Date('2026-10-15')` のようなローカル時間の計算だと、時差でずれることがある
- **6週間分（42日）**：月が変わっても、高さが変わらない。その月の1日が何曜日かで、前の月の日付が何日ぶん入るかを決める
- **今回のバグ：曜日の色**：日付1つずつに「日曜は赤・土曜は青」を付けるとき、**通し番号（0〜41）**で判断していたので、1行目しか色が付かなかった。正しくは、**列の位置（`i % 7`）**。見た目の確認で見つかった。**テストが、曜日の見出しだけを調べていて、日付を調べていなかった**のが原因。直したあと、全ての週を調べるテストを足した
- **カレンダーが見切れた**：カレンダーを、列やモーダルの中に出していたので、その枠（`overflow`）に切り取られた。
  - 対策：`createPortal` で、`body` の直下に出す。位置は `position: fixed`（画面に固定）で、欄の位置（`getBoundingClientRect`）から計算する
  - 欄のすぐ下が基本。下に入らず、上のほうが広いときだけ、上に出す。どちらにも入らないときは、画面の中に収まる位置にずらす。右端からも、はみ出さない
  - 画面の大きさやスクロールが変わったら、位置を決め直す（`resize`、`scroll` のイベント）
- **ポータルとイベント**：ポータルで別の場所に出した部品でも、React のイベントは、元の親に伝わる。そのため、窓の外を押したか調べるときは、`e.target === e.currentTarget`（窓そのものを押したか）で見分けている。一方、`document` に付けた「外を押したか」の判定は、画面の部品の親子ではなく、実際の場所（DOM）で見るので、カレンダーの中かどうかを、別に調べる必要がある
- **Esc の順番**：カレンダーが開いているときの Esc は、カレンダーだけを閉じる。カレンダーは、`document` で、**キャプチャ**（イベントが降りていく途中）で先に受け取り、`stopPropagation()` で、それより先に伝えない。次の Esc で、モーダルが閉じる
- **フォーカスを奪わない**：カード追加の入力欄は、フォーカスが外に出ると、確定または閉じる。カレンダーを触っただけで閉じないよう、`onMouseDown` で `preventDefault()` して、入力欄からフォーカスを動かさない
- **テストで、画面の大きさを決め打ちにする**：テスト環境（jsdom）には、画面の大きさがない。`getBoundingClientRect` と `window.innerHeight` を、テストの中で決めた値に差し替えて、「下／上／画面に収まる位置／右端」を調べた

### やってみよう
1. カードを押して、期限の欄を押す → カレンダーが開く。日付を押すと、すぐに選ばれて閉じる
2. ＜＞で月を移る。曜日と日付の色（日曜は赤、土曜は青）を、全ての週で見る
3. 「期限を外す」で、期限がなくなる
4. カレンダーを開いたまま Esc → カレンダーだけが閉じる。もう一度 Esc → モーダルが閉じる
5. ブラウザの画面を小さくして、画面の下のほうで開く → 上に出る／収まる位置にずれる

## 9. カードの削除（確認メッセージ付き）
編集モーダルの左下に「削除」ボタンを置いた。押すと、**モーダルの中**で「本当に削除しますか？」と確認が出る。「削除する」を押すと、`DELETE /api/cards/{id}` を送り、ボードを取り直して、モーダルを閉じる。

| ファイル | 変更 |
|---|---|
| `api/client.ts` | `deleteCard(id)` を追加。`request()` が、204 のときは JSON を読まずに終わるようにした |
| `components/CardModal.tsx` | 「削除」ボタン、削除の確認、削除中の動きを追加 |

- **204 は、JSONを読めない**：今までの `request()` は、成功すると必ず `response.json()` を呼んでいた。204 No Content は中身が空なので、そのまま読むと失敗する。そこで、`status === 204` のときは、読まずに終わるようにした（バックエンドの学習ノート、13章と対応）
- **確認は、状態（state）で切り替える**：`confirmingDelete` という true / false を持つ。true のときは、いつものボタン（削除・キャンセル・保存）の代わりに、確認の枠（「削除する」「キャンセル」）を出す。`window.confirm`（ブラウザ標準の確認）ではなく、画面の中に出すので、見た目をそろえられて、テストもしやすい
- **確認の「キャンセル」にフォーカス**：確認が出たとき、まず「キャンセル」にフォーカスを置く（`autoFocus`）。Enter を押しても、消えない。取り返しのつかない操作は、安全なほうを初期にする
- **Esc の意味が、場面で変わる**：確認が出ている間の Esc は、確認だけを閉じて、編集に戻る。通常の Esc は、モーダルを閉じる。窓の外を押したときも、同じ。この判断を `dismiss` という1つの関数にまとめた
- **削除中は、閉じない**：保存のときと同じ作り。通信中は `saving` を true にして、ボタンを押せなくする。`savingRef` で、二重に送るのも防ぐ。Esc や窓の外でも、閉じない
- **失敗したら、確認を出したまま**：404 などで失敗したら、エラーを表示して、やり直せるようにした
- **useCallback と依存の配列**：`dismiss` は、`confirmingDelete` の値によって動きが変わる。そのため `useCallback` の依存に `confirmingDelete` を入れた。最初は、ref（`useRef`）に値を写して避けたが、lint に「描画中に ref を書き換えている」と注意された。**値は、state をそのまま使うのが素直**
- テスト：確認が出る（まだ削除されない）／キャンセルで編集に戻る／確認中の Esc は確認だけ閉じる／「削除する」で DELETE が送られ、カードがボードから消える／失敗したらエラーを出す／通信中はボタンが押せず Esc でも閉じない／`deleteCard` が 204 でも失敗しない

### やってみよう
1. DB・バックエンド・画面を起動して、カードを1枚追加する
2. そのカードを押し、「削除」を押す → 確認が出る。「キャンセル」で、編集に戻る
3. もう一度「削除」→「削除する」。カードがボードから消える
4. 確認を出して Esc → 確認だけが閉じる。もう一度 Esc → モーダルが閉じる
5. （発展）バックエンドを止めてから「削除する」を押し、エラーが出ることを見る

## 10. カードのドラッグ＆ドロップ（dnd-kit）
カードをつかんで、別の列へも、同じ列の中でも動かせるようにした。動かした位置は、バックエンドの `PUT /api/cards/{id}/move`（バックエンドの学習ノート、14章）で保存する。

| ファイル | 役割 |
|---|---|
| `components/Board.tsx` | `DndContext`（ドラッグ＆ドロップの全体を管理する入れ物）。つかむ・動かす・置くの処理、先に画面へ反映する仕組み、保存の失敗の扱い |
| `components/BoardColumn.tsx` | 列。`SortableContext`（この列のカードは、縦に並べ替えられる）と、`useDroppable`（列全体が、カードを落とせる場所） |
| `components/CardItem.tsx` | カード。`useSortable`（このカードは、つかめて、並べ替えられる）。見た目は `CardFace` に分けた |
| `lib/moveCard.ts` | 動かした結果の計算（画面を使わない関数） |
| `lib/dragIds.ts` | `card-1`、`column-1` のような目印 |

### dnd-kit の部品
- **`DndContext`**：全体を包む。ここに、「つかんだ」「別の場所の上に来た」「置いた」「取り消した」の処理（`onDragStart` / `onDragOver` / `onDragEnd` / `onDragCancel`）を渡す
- **`useSortable`**：カードに付ける。つかむ操作（`listeners`）と、動いている間の見た目の位置（`transform`）をくれる
- **`useDroppable`**：列に付ける。カードが1枚もない列にも、落とせるようにする
- **`DragOverlay`**：つかんで動かしているカードを、マウスについてくる形で描く。元の場所のカードは、半透明（`opacity-40`）で残す
- **センサー**：マウス（`PointerSensor`）とキーボード（`KeyboardSensor`）。「何を、つかむ操作とみなすか」を決める部品

### 学んだポイント
- **「押す」と「つかむ」の区別**：カードを押すとモーダルが開く。動かさずに離せば「押した」、**5px 動いたら「つかんだ」**（`activationConstraint: { distance: 5 }`）。これがないと、ちょっと動いただけで、モーダルが開かなくなる。それでも、ドラッグの直後に「押した」と受け取られないよう、直後の100ミリ秒は、モーダルを開かない（`justDraggedRef`）
- **つかむ口は、`li` ではなく、中の `button` に付ける**：`listeners` と `attributes` を `li` に付けると、`li` の役割（リストの項目）が変わってしまう。ボタンに付ければ、見出しの読み上げも、今までのテストも、そのまま
- **カードのIDと列のIDは、同じ数字になる**（どちらも 1 から）。dnd-kit は「どれの上にあるか」をIDで教えるので、そのままでは区別できない。そこで、`card-1` と `column-1` のように、前に文字を付けた（`lib/dragIds.ts`）
- **先に画面へ反映し（楽観的更新）、あとで保存する**：置いたとき、保存の結果を待つと、カードが一瞬、元の場所に戻って見える。そこで、先に新しい並びを見せて（`pending`）、保存し、成功したらボードを取り直す。**失敗したら、元の並びに戻して、エラーを出す**
  - `pending` は、「どの `cards` をもとにしたか」（`base`）を一緒に持つ。取り直した新しい `cards` が届くと、`base` と違うので、自動で使われなくなる（消す処理を書かなくてよい）
- **別の列の上に来たら、その場で入れて見せる**：`onDragOver` で、別の列の上に来た時点で、カードをその列に入れる。そうすると、その列のカードが、場所をあけてくれる。同じ列の中の入れ替えは、`SortableContext` が自動でやる
- **列の外で離したら、元に戻る**：`onDragEnd` の `over` が `null`（どこの上でもない）のとき、`pending` を消すだけで、元の並びに戻る（UC-2 の例外の流れ）
- **画面とサーバーで、同じ計算をしている**：`lib/moveCard.ts` は、バックエンドの `moveCard` と同じ考え方（動かすカードを抜く → 差し込む → 連番を振る）。画面の予想と、サーバーの結果が、ずれにくい
- **絞り込み中は、動かせない**：検索で絞り込むと、画面には列の一部のカードしか出ない。「上から何番目に置いたか」が、列全体では分からなくなる。そこで、絞り込み中はつかめないようにして（`disabled`）、ヘッダーの下に、お知らせを出した。つかめるように見えないよう、カーソルの形も変える
- **キーボードでも動かせる**：スペースでつかむ → 矢印で動かす → スペースで置く。Esc で取り消し。**Enter は、モーダルを開くために空けておいた**（Enter でもつかめると、「開く」と「つかむ」がぶつかる）。読み上げの案内の文は、日本語にした（`accessibility`）
- **テスト**：`lib/moveCard.test.ts` で、計算を単体で調べる（別の列／同じ列／空の列／範囲外／負の position）。画面のテストは、jsdom には画面上の位置がないので、`getBoundingClientRect` を差し替えて、「列は横に、カードは縦に並んでいる」ことにし、**キーボードで動かして**、送られた内容と、並びを調べた
  - マウスでのドラッグは、jsdom では再現しにくいので、ブラウザで確認する

### やってみよう
1. DB・バックエンド・画面を起動する
2. カードを、マウスでつかんで、同じ列の中で動かす → 画面を読み込み直しても、位置が残る
3. 別の列へ動かす。カードがない列にも、動かす
4. 列の外で離す → 元の位置に戻る
5. カードを動かさずに、短く押す → モーダルが開く
6. カードにフォーカスして、スペース → 矢印 → スペースで、キーボードでも動かす
7. キーワードで検索する → お知らせが出て、カードが動かせない。「クリア」で、動かせるようになる
8. （発展）バックエンドを止めて、カードを動かす → エラーが出て、元の並びに戻る
