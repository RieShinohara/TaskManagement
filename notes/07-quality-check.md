# 07 品質チェック：「動く」から「ちゃんとしている」へ

機能がすべてできたあと、**作ったものの品質を、あらためて点検**した。ここでは、点検の考え方と、入れた道具、学んだことをまとめる。
点検の結果の一覧は、[docs/quality-review.md](../docs/quality-review.md)。

## 1. 品質チェックとは
「動いている」ことと、「ちゃんとしている」ことは、別である。たとえば、次のようなことがある。
- 動くけれど、**標準的なやり方から外れている**（あとから読む人が、戸惑う）
- 動くけれど、**ある条件のときだけ壊れる**（Tab キーで操作したとき、同時に操作したとき、など）
- 動くけれど、**文書と食い違っている**（文書を信じた人が、間違える）

そこで、(1) 人が読んで点検する、(2) **道具に、自動でチェックしてもらう**、の2つを組み合わせる。

## 2. 道具：静的チェック（リント）
プログラムを**動かさずに**、書き方だけを調べる道具を、**静的解析**（リント、lint）と呼ぶ。人が毎回見なくても、決まりごとを守っているか、バグになりやすい書き方がないかを、機械が調べてくれる。

| 対象 | 道具 | 調べること |
|---|---|---|
| 画面 | oxlint | React の決まり（フックの使い方など）、アクセシビリティ（`jsx-a11y`） |
| サーバー | Checkstyle | 書き方の決まり（使っていない import、名前のつけ方など） |
| サーバー | SpotBugs | バグになりやすい書き方 |
| サーバー | JaCoCo | テストで、どのコードが実行されたか（カバレッジ） |

実行のコマンド：画面は `npm run lint`、サーバーは `.\gradlew.bat check`（テストも一緒に走る）。

## 3. 学んだポイント
- **警告も失敗にする**：`oxlint --deny-warnings`。警告は、放っておくと増えて、誰も見なくなる。「警告 0 件」を保つほうが、新しい問題に気づける
- **最初はゆるく、少しずつ厳しく**：Checkstyle は、既存のコードに合わせた、ゆるい規則から始めた。厳しい規則を一度に入れると、直すものが多すぎて、本来の目的（バグを減らす）から離れてしまう
- **誤検知は、理由を書いて除外する**：SpotBugs が 9 件の警告を出したが、Spring の「部品を渡す仕組み（DI）」と、リストを持つ record への、定番の誤検知だった。**黙って消さず、除外した理由を、設定ファイルに書く**。lint の除外コメントも同じ（`oxlint-disable-next-line 規則名 -- 理由`）
- **規則を入れたら、既存のコードがひっかかる**：画面の lint では 13 件、サーバーのテストでは、使っていない import が 1 件見つかった。ひっかかったものは、(1) 直す、(2) 理由を書いて除外する、(3) 規則を外す、のどれかを選ぶ。挙動が変わる直し方（例：窓を `<dialog>` に置き換える）は、この作業に混ぜず、別の課題にした
- **道具が新しい Java に対応しているかを、先に確かめる**：Java 25 は新しいので、導入する前に、各道具が動くかを試した（動いた）
- **「実装が正」と「設計書が正」を、場合によって使い分ける**：文書と実装がずれていたら、基本は、実際に動いている実装に文書を合わせる。ただし、**設計書のほうが良い**と判断したもの（ドロップ先の青い線）は、実装を設計書に合わせる。どちらが正かは、人（ユーザー）が決める
- **1 つの目的は 1 つの PR**：品質チェックの結果を反映する作業は、1 つの Issue・1 つの PR にまとめた（途中で、文書だけが古いままの状態を作らないため）。コミットは、領域（画面、サーバー、文書）ごとに分けた。一方、動作が変わる「青い線」は、目的が違うので、別の Issue にする

## 4. やってみよう
1. `frontend/` で `npm run lint` を実行する。警告が 0 件で終わるか
2. `backend/` で `.\gradlew.bat check` を実行する。終わったら、`build/reports/jacoco/test/html/index.html` をブラウザで開く。どのクラスが、どのくらいテストされているか
3. `backend/build/reports/checkstyle/main.html` を開く。違反が 0 件であることを確かめる
4. わざと、使わない `import java.util.Map;` を、テストのファイルに足して、`.\gradlew.bat checkstyleTest` を実行する。どう失敗するか（確認したら、元に戻す）
