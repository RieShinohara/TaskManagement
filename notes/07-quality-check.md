# 07 品質チェック：「動く」から「ちゃんとしている」へ

機能がすべてできたあと、**作ったものの品質を、あらためて点検**した。ここでは、点検の考え方と、入れた道具、学んだことをまとめる。
点検の結果の一覧は、[docs/quality-review.md](../docs/quality-review.md)。

## 1. 品質チェックとは
「動いている」ことと、「ちゃんとしている」ことは、別である。たとえば、次のようなことがある。
- 動くけれど、**標準的なやり方から外れている**（あとから読む人が、戸惑う）
- 動くけれど、**ある条件のときだけ壊れる**（Tab キーで操作したとき、同時に操作したとき、など）
- 動くけれど、**文書と食い違っている**（文書を信じた人が、間違える）

そこで、(1) 人が読んで点検する、(2) **道具に、自動でチェックしてもらう**、の2つを組み合わせる。

## 2. 道具：静的チェック（リント）
プログラムを**動かさずに**、書き方だけを調べる道具を、**静的解析**（リント、lint）と呼ぶ。人が毎回見なくても、決まりごとを守っているか、バグになりやすい書き方がないかを、機械が調べてくれる。

| 対象 | 道具 | 調べること |
|---|---|---|
| 画面 | oxlint | React の決まり（フックの使い方など）、アクセシビリティ（`jsx-a11y`） |
| サーバー | Checkstyle | 書き方の決まり（使っていない import、名前のつけ方など） |
| サーバー | SpotBugs | バグになりやすい書き方 |
| サーバー | JaCoCo | テストで、どのコードが実行されたか（カバレッジ） |

実行のコマンド：画面は `npm run lint`、サーバーは `.\gradlew.bat check`（テストも一緒に走る）。

## 3. 学んだポイント
- **警告も失敗にする**：`oxlint --deny-warnings`。警告は、放っておくと増えて、誰も見なくなる。「警告 0 件」を保つほうが、新しい問題に気づける
- **最初はゆるく、少しずつ厳しく**：Checkstyle は、既存のコードに合わせた、ゆるい規則から始めた。厳しい規則を一度に入れると、直すものが多すぎて、本来の目的（バグを減らす）から離れてしまう
- **誤検知は、理由を書いて除外する**：SpotBugs が 9 件の警告を出したが、Spring の「部品を渡す仕組み（DI）」と、リストを持つ record への、定番の誤検知だった。**黙って消さず、除外した理由を、設定ファイルに書く**。lint の除外コメントも同じ（`oxlint-disable-next-line 規則名 -- 理由`）
- **規則を入れたら、既存のコードがひっかかる**：画面の lint では 13 件、サーバーのテストでは、使っていない import が 1 件見つかった。ひっかかったものは、(1) 直す、(2) 理由を書いて除外する、(3) 規則を外す、のどれかを選ぶ。挙動が変わる直し方（例：窓を `<dialog>` に置き換える）は、この作業に混ぜず、別の課題にした
- **道具が新しい Java に対応しているかを、先に確かめる**：Java 25 は新しいので、導入する前に、各道具が動くかを試した（動いた）
- **「実装が正」と「設計書が正」を、場合によって使い分ける**：文書と実装がずれていたら、基本は、実際に動いている実装に文書を合わせる。ただし、**設計書のほうが良い**と判断したもの（ドロップ先の青い線）は、実装を設計書に合わせる。どちらが正かは、人（ユーザー）が決める
- **1 つの目的は 1 つの PR**：品質チェックの結果を反映する作業は、1 つの Issue・1 つの PR にまとめた（途中で、文書だけが古いままの状態を作らないため）。コミットは、領域（画面、サーバー、文書）ごとに分けた。一方、動作が変わる「青い線」は、目的が違うので、別の Issue にする

- **手順は、スキルにして残す**：今回の進め方（調べる → 静的チェックを動かす → 記録する → 文書を直す → PR）を、プロジェクト用のスキル `quality-check`（`.claude/skills/quality-check/SKILL.md`）にした。次に点検するときは、同じ手順で、抜けなく進められる。**スキルは、「やり方の説明書」を、Claude Code が読める形で置いたもの**で、チームの決まりごとを、毎回言い直さなくてよくなる

- **指摘は、再現して確かめてから直す**：品質チェックの F2「Tab でカレンダーに移ると、誤って確定する」を直そうとして、先に再現テストを書いたところ、**起きなかった**。カレンダーは画面の末尾に描かれるので、Tab ではカレンダーに移れず、欄の外の部品に移る（その結果の確定は、設計どおり）。読んだだけの指摘は、外れることがある。**直す前に、問題を再現できるかを確かめる**。再現できなければ、直さずに、「こういう動きだ」とテストに残す。なお、このときの本当の問題は、カレンダーにキーボードで入れないこと（F6）だった
- **見えない出力を、テストの失敗メッセージで見る**：テストの中の `console.log` が画面に出ない設定のときは、調べたい値を文字列にためて、`expect(...).toBe('')` でわざと失敗させると、値が表示される（調べ終わったら、ちゃんとしたテストに書き換える）

## 4. やってみよう
1. `frontend/` で `npm run lint` を実行する。警告が 0 件で終わるか
2. `backend/` で `.\gradlew.bat check` を実行する。終わったら、`build/reports/jacoco/test/html/index.html` をブラウザで開く。どのクラスが、どのくらいテストされているか

## 5. 整形（Prettier）と CI（品質チェック F9）
### Prettier：見た目を、自動でそろえる
- **リント（oxlint）との違い**：リントは、「間違いやすい書き方」を見つける道具。Prettier は、**見た目（インデント、改行の位置、クォートの種類）**を、自動でそろえる道具。見た目の好みで、人が議論しなくてよくなる
- **設定は、今のコードに合わせた**：セミコロンなし、シングルクォート、1行120文字、末尾のカンマあり。先に、書き込まずに測った：120文字なら、56ファイルのうち**18ファイル・約114行**だけが変わる（100文字なら35ファイル）。差分が小さいほど、レビューが楽で、間違いが紛れ込みにくい
- **`endOfLine: auto`が必要だった理由**：この PC は、Git の設定（`core.autocrlf=true`）で、作業フォルダのファイルは CRLF、Git の中身は LF。Prettier の既定は「LF 以外は違反」なので、そのままだと、**この PC では全ファイルが違反**になる。`auto` にして、今ある改行を、そのまま使う
- **`format`（整形する）と `format:check`（確かめる）**：確かめるだけのコマンドは、何も書き換えない。CI は、こちらを使う
- **整形だけの PR は、動きを変えない**：整形の前後で、テスト（197件）・lint・build が、同じ結果であることを確かめた。**差分の大きい整形は、機能の変更と、同じ PR に混ぜない**（どこが本当の変更か、分からなくなるため）
- **版を固定した**：`prettier` は、`3.9.10`（`^` を付けない）。版が上がると、整形の結果が変わることがあるため。出て15日たった版を選んだ

### CI：PR のたびに、自動で確かめる
- **CI（継続的インテグレーション）**：変更が入るたびに、テストなどを、自動で走らせる仕組み。人が、確認を忘れても、抜けても、機械が確かめる。GitHub では、**GitHub Actions** という名前で、`.github/workflows/ci.yml` に、手順を書く
- **構成**：`backend`（`gradlew check`）と `frontend`（`npm ci` → lint → 整形の確認 → test → build）の2つのジョブが、**並んで**走る。PR のページの「Checks」で、✓ か ✗ が見られる
- **使う部品は、コミットの ID で固定した**：`uses: actions/checkout@3d3c42e…  # v7.0.1`。版の名前（`v7`）は、あとから、別の中身に差し替えられることがある。ID なら、差し替えられない。悪意のある差し替えを、知らずに実行するのを防ぐ。出たばかりの版も避けた
- **権限は、読み取りだけ**（`permissions: contents: read`）。秘密情報も使わない
- **Windows では動いて、Linux では動かない、落とし穴を先に潰した**：①`gradlew` に**実行権限**がなかった（Windows には、実行権限の考え方がない）。Git に、実行権限つきで登録し直した ②CI には `.env` がないので、`POSTGRES_PASSWORD` を、ダミー値で渡した（テストの DB は使い捨てなので、ダミーでよい）
- **手元では、CI を動かせない**：だから、PR を作って、**PR の上で、初めて動かした**。結果は、1回目で成功した。ログで、本当にテストが走ったこと（`:test` が `UP-TO-DATE` ではない）を確かめた。**緑の ✓ だけで、安心しない**
- **注意書き（注釈）を、見落とした**：最初に、「気になる警告なし」と書いたが、PR の画面に出ていた「💬 2」を、見ていなかった。中身は、「`ubuntu-latest` が、Ubuntu 26 に切り替わっていく」というお知らせだった。今回は24.04で成功していたが、26 での動作は未確認なので、**確かめて成功した `ubuntu-24.04` に固定**した。`latest` は、気づかないうちに、中身が変わる
- **CI が通らないとマージできない設定（必須チェック）を入れた**（Issue #130。2026-10-26）：GitHub の「ブランチの保護」の設定。`backend` と `frontend` の2つが、どちらも ✓ でないと、PR のマージボタンが押せない。**管理者（自分）にも適用**される。これで、テストが落ちた変更を、うっかりマージする事故が、仕組みで防げる
  - 入れなかったもの：「ブランチを最新にしないとマージできない」（strict）。1人開発では、面倒が増えるだけ
  - **落とし穴**：①CI 自体が壊れる（GitHub の障害や、設定のミス）と、マージが止まる。そのときは、設定を一時的に外す手順が要る ②`ci.yml` のジョブの名前を変えると、必須のチェックが「見つからない」状態になり、永遠に待つ。名前を変えるときは、設定も直す ③設定を変える前に、今の設定を、ファイルに保存しておいた（戻せるように）

`npm install` のあとに、`npm audit` が、**高（high）の脆弱性を1件**報告した（`undici`）。`jsdom`（テスト用の部品）が連れてくるもので、`npm audit --omit=dev`（本番に入る部品だけ）は **0件**。今回の整形の追加が、原因ではない（追加の前から、同じ1件）。F9 とは別の話なので、直していない

### 画面の重複を整理する（F8。Issue #132）
- **同じ決まりは、1か所に書く**：`'完了'`（期限が過ぎても赤くしない列）と、文字数の上限（255・2000）が、2つのファイルに別々に書いてあった。片方だけ直すと、食い違う。`lib/cardRules.ts` にまとめた
- **同じ式は、名前のある関数にする**：「完了列でない・期限がある・過ぎている」という判定が2か所にあった。`isCardOverdue` にして、**先にテストを書いた**（関数がまだないので、最初は赤。作ると緑）。動きを変えない整理は、前後でテストが同じ結果になることで確かめる
- **`as`（型の読み替え）は、嘘をつける**：`value as BackupFile` は、中身を調べずに「これは BackupFile だ」とコンパイラに言い張る。代わりに、**型ガード**（`value is BackupFile` を返す関数）にして、中身を調べた結果で型を決める。背景画像の割り当て先は、一覧を `as const` で書き、型をそこから作ると、キャストが要らなくなる
- **`useCallback` は、足さなかった**：関数を固定すると、`memo` などで比べる相手があるときだけ、再描画が減る。このアプリは、どちらも使っていないので、足しても効果がない。**「やらない」と決めて、理由を記録する**のも、品質の仕事

### 読み上げソフトに知らせる（F8の後半。Issue #134）
- **読み上げソフト（スクリーンリーダー）**：画面の内容を、音声で読み上げるソフト（Windows のナレーター、NVDA、iPhone の VoiceOver など）。目が見えない・見えにくい人が、耳で聞いて操作する。ソフトが読むのは、見た目ではなく、HTML に書かれた**名前と役割**
- **問題**：「バックアップを読み込みました。」は、画面の右下に出るだけだった。見える人には分かるが、読み上げソフトを使う人は、成功したのか分からない
- **直し方**：`role="status"`（「中身が変わったら、知らせてほしい場所」という目印）を付けた。**入れ物は、いつも画面に置いておき、中身だけを出し入れする**。お知らせが出るときに入れ物ごと作ると、読まれないソフトがある
- **テストで確かめられること／られないこと**：「入れ物が最初からあり、成功すると中に文言が入り、閉じると消える」はテストできる。**実際の聞こえ方は、人が確かめるしかない**
- **見つけたこと**：テストで `role="status"` を探したら、2つ見つかった。もう1つは、ドラッグ操作の部品（dnd-kit）が、自分で置いていた読み上げ用の入れ物（ドラッグ中の「持ち上げました」などを知らせる）。自分で付けていない部品が、画面に要素を足すこともある
- **やってみよう**：Windows のナレーター（Win + Ctrl + Enter で起動／同じキーで終了）をつけて、バックアップを読み込む。完了のお知らせが読み上げられるか

### 厳しすぎる検査は、やらないと決めてもよい：`noUncheckedIndexedAccess`（F9の残り。Issue #136）
- **何をする設定か**：配列の `names[0]` を取り出すとき、「中身が無いかもしれない」と、TypeScript に厳しく見てもらう。今は、`names[0]` は「必ずある」扱いで、空の配列から取り出しても、書いた時点では気づけず、**実行して落ちる**。有効にすると、型が `string | undefined` になり、**書いた時点で、確認を書かされる**
- **測ってから決めた**：有効にして試すと、22件のエラー（本番のコード8件、テスト14件）。直すには、動きを、テストで守ってから直す必要がある
- **やらないと決めた理由**：このアプリは、「空だったとき」に落ちる場面がほとんどなく、実害が起きる可能性が低い。作業に見合わない。**品質の検査は、増やすほど良いわけではない**。得られるものと、かかる手間を比べて、決める（B14 と同じ考え方）。決めた理由は、`docs/quality-review.md` に残した

### PowerShell で `npm` が止まったとき：`npm.cmd`
- **症状**：`npm run dev` と打つと、「このシステムではスクリプトの実行が無効になっているため、ファイル …
pm.ps1 を読み込むことができません」と出る（`PSSecurityException` / `UnauthorizedAccess`）
- **原因**：Windows の `npm` は、`npm.ps1`（PowerShell のスクリプト）と `npm.cmd`（昔からある Windows の命令書）の2つで入っている。`npm` と打つと、PowerShell は、先に `npm.ps1` を探すが、PowerShell は、安全のため、初期設定で、スクリプトの実行を禁止している
- **直し方**：拡張子まで書いて、**`npm.cmd run dev`** と打つ。働きは同じで、設定は変えない。`npm test` → `npm.cmd test`、`npx` → `npx.cmd`。`node`・`git`・`gradlew.bat` は、`.ps1` ではないので、そのままで動く
- **設定を変える方法**：`Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`（1回だけ。自分のユーザーだけに効く）。必須ではない
- **README やコマンド表は、`npm` のまま**：Mac など、ほかの環境の人にも通じる書き方なので。止まったら、この対処をする

### アクセシビリティの自動検査（F7。Issue #138）
- **何をしたか**：テストの中で、画面を`axe-core`（アクセシビリティの検査の定番）にかけて、「名前のないボタン」「ラベルのない入力欄」「代替文字のない画像」などの違反を、機械に見つけさせる。主な7画面に当てた
- **道具の選び方**：`vitest-axe` というラッパーもあるが、最後の更新が約1年前で止まっている。本体の `axe-core` を直接使い、小さな関数（`expectNoA11yViolations`）を、自分で1つ書いた。版は固定した（出て21日たったもの）
- **先に測った**：違反は0件だった。lint の `jsx-a11y`（書いた時点で見つける）と、これまでの作りで、多くを防げていた。**0件でも、検査が働いているとは限らない**。そこで、**わざと違反を入れて、赤になること**を確かめ、そのテストも残した。「いつも通る検査」は、ないのと同じ
- **自動検査の限界**：テストの環境（jsdom）は、本物のブラウザではないので、**色のコントラスト（見やすさ）や、画面の配置は、検査できない**。自動で見つかる問題は、全体の一部と言われる。**読み上げソフトでの聞こえ方は、人が確かめるしかない**
- **lint と axe の違い**：lint は、**コードを読んで**、書いた時点で見つける（速い）。axe は、**実際に出た画面を見て**、見つける（動的に作られる部分も見られる）。両方あると、見落としが減る

### カバレッジ：テストが、どこまで通ったか（F7の後半。Issue #140）
- **カバレッジ**：テストを動かしたとき、コードの**どの行・どの分岐が、実際に実行されたか**の割合。サーバーの JaCoCo の、画面版（`@vitest/coverage-v8`）。`npm run test:coverage` で出る。詳しい表は、`coverage/index.html` をブラウザで開く（実行されなかった行が、赤く見える）
- **測った数字**：行95.8%・文94.5%・関数96.7%・分岐89.2%。分岐は、`if` の「はい」「いいえ」の両方を通ったか。一番低くなりやすい
- **100% を目指さなかった**：`image.ts`（画像の縮小）は、本物のブラウザの描画機能が要り、テストの環境（jsdom）では動かせない。`main.tsx`（起動の入口）は、動かす意味がない。**数字を上げるために、意味のないテストを書くのは、本末転倒**
- **しきい値（これを下回ると失敗する数字）**：測った数字より、少し下に置いた（行・文・関数90%、分岐80%）。置く理由は、**あとで、テストを書かずにコードを増やしたとき、CI が気づかせてくれる**から。ぴったりにすると、小さな変更でも失敗して、うるさい。わざと高い値にして、本当に失敗することも確かめた
- **CI では、`npm test` を置き換えた**：テストは1回だけ動かし、同時に数字も出す。しきい値を置いても、CI で動かさなければ、意味がない
- **カバレッジが高い ≠ 品質が高い**：「通った」だけで、「正しく確かめた」とは限らない（`expect` のないテストでも、数字は上がる）。**低い所を見つける道具**として使う
- **やってみよう**：`npm.cmd run test:coverage` を実行し、`coverage/index.html` を開いて、`image.ts` の、赤い行を見る

### 画像は、開く前に調べる（F5の前半。Issue #142）
- **画像爆弾（decompression bomb）**：ファイルは小さいのに、開くと巨大になる画像。PNG は、同じ色が続くと、すごく小さく圧縮できる。3万×3万 px の白い PNG は、**107KB**だが、開くと9億画素で、メモリを約3.6GB使う。ブラウザのタブが固まる・落ちる。これまでは、ファイルの大きさ（20MB）しか見ていなかったので、通ってしまった
- **開いてからでは遅い**：`createImageBitmap` は、開いた時点でメモリを使う。だから、**開く前に**、ファイルの先頭だけを読んで、縦横の大きさを調べる。PNG は先頭の24バイト、JPEG は区切りをたどって SOF という部分、WebP は3種類（VP8・VP8L・VP8X）に、縦横が書いてある
- **ファイルの中身は、ただのバイト列**：「何バイト目に、何が書いてあるか」を決めた規格（フォーマット）がある。それを読むだけなので、**画像を描く機能（canvas）がない jsdom でも、テストできる**。作った小さなバイト列で確かめ、本物の JPEG でも確かめた
- **上限の決め方**：5000万画素。開くと、1画素あたり4バイトで、約200MB。8K（3,300万画素）と、48MP のスマホ写真は通る。1億画素にすると約400MBで、古い PC には重い
- **「読めないものは弾く」にした**：縦横が読めないファイルを通すと、検査をすり抜ける道ができる。安全側に倒した。そのかわり、本物の画像を弾かないよう、先頭は1MB まで読む（JPEG は、縦横の前に、EXIF などが長く入ることがある）
- **古いテストを、直した**：これまでのテストは、中身が「image-bytes」という文字だけの偽の画像だった。先頭を読むようにしたので、テスト用の画像も、先頭だけは本物の形にした（`test-utils/imageBytes.ts`）。**検査を足すと、それまで「通っていた」偽物のデータが、通らなくなる**
- **やってみよう**：ユーザーが、107KB の巨大な画素数の PNG を、背景に登録してみて、「画像が大きすぎます（5000万画素まで）。」と出ることを確かめる

### バックアップは、読む前に調べる（F5の後半。Issue #144）
- **`file.size` は、読まなくても分かる**：ファイルを選んだ時点で、大きさは分かっている。`text()` は、中身を全部メモリに読み込む。だから、**大きさを先に見て、大きすぎれば、読まずに断る**。20MB は、ふつうのバックアップ（数KB〜数MB）より、ずっと大きい余裕のある上限
- **「読んでいない」ことを、テストで確かめる**：`vi.spyOn(file, 'text')` で、`text()` が呼ばれたかを記録し、`not.toHaveBeenCalled()` で、呼ばれていないことを確かめた。結果の文言だけを見ても、「読まずに断った」のか「読んでから断った」のか、区別できない
- **`version`（版）**：ファイルの形は、アプリが成長すると、変わることがある。そのとき、古いアプリが新しい形を読むと、壊れる。そこで、ファイルに `version` を書き、**対応している版だけ**を受け付ける。画面でも調べる理由は、サーバーに送って400で断られるより、**早く、分かりやすく**伝えられるから。ただし、サーバーも、もう一度調べる（画面の検査は、ユーザーの親切のため。守りの本番は、サーバー）
- **「ない」「文字の `"1"`」も、対応していない**：`file.version === 1` と、厳密に比べた。数字の1だけが、対応している版
- **やってみよう**：`version` を `2` に書き換えたバックアップを選んで、「対応していないバージョンです。」と出ることを確かめる
