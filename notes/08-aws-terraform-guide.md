# 08 AWS と Terraform でデプロイする：初めての人のための解説と手順

このアプリを、**AWS（アマゾンのクラウド）** に置いて、インターネットから使えるようにする。
ただし、AWS の管理画面（マネジメントコンソール）をポチポチ操作するのではなく、**コマンドと設定ファイル**で行う。それを AI（Claude Code）にやってもらう。
この章は、そのための**予備知識と、準備の手順**をまとめたもの。

> 状況（2026-10-28）：準備の段階。AWS には、まだ何も作っていない（費用ゼロ）。
> 認証の方式は、**まず講義と同じ「専用 IAM ユーザーのアクセスキー」**にする（SSO は、あとで試す）。デプロイ先の構成は、**講義を確認してから決める**。構成の候補は [docs/deploy-options.md](../docs/deploy-options.md)。

## 1. IaC（アイエーシー）とは
**Infrastructure as Code（インフラをコードで管理する）** の略。

「インフラ」とは、アプリが動くための土台のこと（サーバー、データベース、ネットワークなど）。
管理画面で手作業で作ると、次の困りごとがある。

| 手作業（管理画面） | IaC（コードで書く） |
|---|---|
| 何をクリックしたか、あとで分からなくなる | 設定ファイルが、そのまま記録になる |
| もう一度同じものを作るのが大変。ミスも起きる | 同じファイルを実行すれば、同じものができる |
| 誰が、いつ、何を変えたか分からない | Git で履歴が残る。PR でレビューもできる |
| 片付け忘れて、お金がかかり続ける | 1コマンドで、全部消せる |

つまり、このプロジェクトで、アプリのコードを Issue → PR で育ててきたのと**同じやり方を、インフラにも使える**、ということ。

## 2. AWS の基本用語
AWS には200以上のサービスがあるが、このアプリで関係しそうなものだけ、先に覚える。

| 用語 | 意味 | このアプリでは |
|---|---|---|
| **リージョン** | AWS の拠点の地域（東京は `ap-northeast-1`） | どこに置くか。日本から使うので、東京が候補（講義に合わせる） |
| **IAM** | 「誰が、何をしてよいか」を決める仕組み | 作成済みの `rie-admin` と、`Administrators` グループ |
| **ポリシー** | 許可・禁止のルールの書類 | `AdministratorAccess`、`DenyBillingAndAccountClosure` |
| **IAM ロール** | 人やサービスが、**一時的に**権限を借りる仕組み | サーバーに、必要な権限だけを持たせる |
| **S3** | ファイルを置く倉庫 | 画面（ビルドした HTML・JS・CSS）を置く |
| **CloudFront** | 世界中に、ファイルを速く配る仕組み（CDN） | 画面の配信。HTTPS にもできる |
| **EC2** | AWS 上の仮想サーバー（1台のパソコン） | バックエンド（Spring Boot）を動かす |
| **ECS / Fargate** | コンテナ（Docker）を、サーバー管理なしで動かす | バックエンドの置き場所の候補 |
| **RDS** | AWS が管理してくれるデータベース | PostgreSQL の置き場所の候補 |
| **VPC** | AWS の中の、自分専用のネットワーク | 外から見える所と、見えない所を分ける |
| **セキュリティグループ** | 通信の出入りの許可リスト（ファイアウォール） | 「DB には、サーバーからだけつなげる」など |
| **ALB** | 通信を、複数のサーバーに振り分ける入口 | バックエンドの入口の候補 |

覚え方：**「何を置くか」→ S3、「どこで動かすか」→ EC2 か ECS、「データはどこか」→ RDS か同居、「誰が触れるか」→ IAM とセキュリティグループ**。

## 3. AWS CLI とは
AWS を、**コマンドで操作する道具**。管理画面でできることは、ほぼ全部できる。

```
aws s3 ls                       自分の S3 の倉庫を一覧する
aws sts get-caller-identity     「いま、だれとして操作しているか」を確認する
```

`aws sts get-caller-identity` は、**まず最初に打つコマンド**。ログインできているか、別のアカウントを触っていないかを確かめられる（出てくるアカウント ID は、他人に見せない）。

Terraform も、実は、**裏で AWS CLI と同じ認証の情報を使って**、AWS とやり取りする。だから、先に AWS CLI の認証を整える。

## 4. Terraform とは
IaC の道具の1つ（HashiCorp 社製）。**「こういう状態にしたい」と設定ファイル（`.tf`）に書くと、AWS をその状態にしてくれる**。

### 4.1 用語
| 用語 | 意味 |
|---|---|
| **provider** | Terraform が、どのサービス（AWS など）を操作するかの部品 |
| **resource** | 作りたい物1つ（例：S3の倉庫1つ、EC2 1台） |
| **variable** | 設定ファイルに外から渡す値（例：リージョン） |
| **output** | 作ったあとに表示したい値（例：サーバーのアドレス） |
| **state（状態ファイル）** | 「Terraform が、いま何を作ったか」の記録（`terraform.tfstate`） |

設定ファイルの見た目（イメージ。これは**例**で、まだ作らない）：

```hcl
provider "aws" {
  region = "ap-northeast-1"
}

resource "aws_s3_bucket" "frontend" {
  bucket = "my-example-bucket-name"   # 世界で1つだけの名前にする
}
```

### 4.2 4つのコマンド（この順に使う）
| コマンド | 何をする | AWSに変化は？ |
|---|---|---|
| `terraform init` | 準備（provider の部品をダウンロード） | なし |
| `terraform plan` | 「こう変わります」という**予告**を表示 | なし |
| `terraform apply` | 予告どおりに、**実際に作る・変える** | **あり（費用が発生しうる）** |
| `terraform destroy` | 作ったものを、**全部消す** | **あり（削除）** |

**`plan` を必ず読む**。`+` は作る、`~` は変更、`-` は削除。「データベースが消える」ような行がないか、`apply` の前に人の目で確かめる。

### 4.3 state の注意
- state には、**パスワードなどの秘密が入ることがある**。このリポジトリは**公開**なので、`*.tfstate` は**絶対にコミットしない**（`.gitignore` で除外する）
- 本格的な運用では、state を S3 に置いて共有する。学習の最初は、手元のファイルでよい
- state を消す・失くすと、Terraform が「何を作ったか」を忘れる。AWS に物が残って、お金がかかり続けることがある

## 5. 認証：AWS に「自分だ」と伝える方法
AWS CLI と Terraform が、AWS を操作するには、**認証**が要る。方式は主に2つ。

| | IAM Identity Center（SSO） | アクセスキー |
|---|---|---|
| 仕組み | ブラウザでログインして、**数時間で切れる一時的な鍵**をもらう | 長い文字列の鍵（ID とシークレット）を PC に置く |
| 安全性 | 高い。PC に長期の鍵が残らない | 低め。**漏れると、他人が自由に使える** |
| 設定の手間 | やや多い（最初に Identity Center の設定が要る） | 少ない |
| 向いている場面 | 人が使う、普段の操作 | 古い仕組み。なるべく避ける |

方針（2026-10-28 に決定）：
- **まず、講義と同じ「専用 IAM ユーザーのアクセスキー」で進める**。仕組みが単純で、「認証とは何か」を体験できる。ルートユーザーのキーは、**絶対に作らない**
- **SSO は、あとで試す**（コースの最終課題などで。先生に聞いてみる）。どちらも経験しておく。認証の方式は、アプリのコードとは別の話なので、Terraform の `.tf` はほぼそのままで、切り替えられる
- 注意：アクセスキーは、**MFA では守れない**。漏れると、MFA に関係なく使われる。特にこのリポジトリは公開なので、キーを書いたファイルを誤ってコミットすると、数分で悪用されることがある。5.3 のルールを守る
- 参考：AWS CLI には、IAM ユーザーが「コンソールのログイン情報」で CLI にログインする機能（`aws login`）も、新しく追加されている。使うなら、公式ドキュメントで確かめてから

### 5.1 アクセスキー方式の手順（講義の方式）
1. AWS の管理画面（IAM）で、**CLI 用の IAM ユーザー**を作る（講義の例：`terraform-deployer`）。ログイン用のユーザー `rie-admin` とは、**別にする**
2. 作ったユーザーを、`Administrators` グループに入れる（請求と解約を禁止するポリシー `DenyBillingAndAccountClosure` が、同じように効く）。講義では `AdministratorAccess` を付ける（学習用。本番に近づけるときは、権限を絞る）
3. そのユーザーの「セキュリティ認証情報」から、**アクセスキーを作成**する（用途は「コマンドラインインターフェイス（CLI）」）。**アクセスキー ID とシークレットアクセスキー**が表示される。シークレットは、この画面でしか見られない
4. 手元で `aws configure` を実行して、4つを入力する：Access Key ID、Secret Access Key、リージョン（`ap-northeast-1`＝東京）、出力形式（`json`）
5. `aws sts get-caller-identity` で、作ったユーザーとして認識されているか確認する（結果のアカウント ID は、他人に見せない）

キーを表示する画面（3 の画面）は、**画面共有・スクリーンショットで、人やチャットに見せない**。

### 5.2 SSO を選んだ場合の手順（流れ。あとで試す）
1. AWS の管理画面で、IAM Identity Center を有効にして、ユーザーと権限（許可セット）を作る
2. 手元で `aws configure sso` を実行して、案内に従う（リージョンなどを聞かれる）。プロファイル名を決める（例：`taskboard`）
3. `aws sso login --profile taskboard` でブラウザが開く → ログイン（MFA も使う）
4. `aws sts get-caller-identity --profile taskboard` で確認
5. Terraform には、`AWS_PROFILE=taskboard` を環境変数で渡す、または provider に `profile = "taskboard"` と書く

### 5.3 認証の情報を守るルール（AI に任せるときも同じ）
- アクセスキー、アカウント ID、QR コード、パスワードを、**チャットに貼らない・リポジトリに入れない**
- キーは、`aws configure` が作るファイル（`~/.aws/credentials`）にだけ置く。メモ帳・文書・`.tf`・`.env` に書かない
- 使わなくなったら、キーを**無効化して削除**する（IAM の画面から）。コース修了後も、残さない
- 漏れたかもしれないと思ったら、すぐ IAM で**キーを無効化**して、ユーザーに相談する
- 認証の情報は `C:\Users\<ユーザー名>\.aws\` に保存される。ここは**コミットしない**（リポジトリの外にあるので、ふつうは入らない）
- 画面や出力を貼るときは、アカウント ID と ARN を**隠す**

## 6. 道具の導入（Windows）
PowerShell で実行する。

```powershell
winget install Amazon.AWSCLI
winget install Hashicorp.Terraform
```

入れたら、**PowerShell（Cursor のターミナル）を開き直して**、確認する。

```powershell
aws --version
terraform -version
```

どちらも、バージョンが表示されればよい。「見つからない」と出たら、開き直しが足りないことが多い。

## 7. 最初の Terraform 体験（費用ゼロ）
まず、**AWS に何も作らない**操作だけで、流れを知る。

1. 空のフォルダ（このリポジトリの外でもよい）に `main.tf` を作り、provider だけを書く
2. `terraform init`：provider の部品がダウンロードされ、`.terraform/` ができる
3. `terraform validate`：書き方が正しいか調べる
4. `terraform plan`：何も作らないので、「変更なし」と出る

**ここまでなら、料金はかからない**。`apply` は、構成を決めてから。

## 8. AI（Claude Code）にデプロイさせるときの安全ルール
AI は速いが、間違えることもある。AWS は**お金がかかり、消すと戻らない**ので、次を守る。

1. **`plan` の結果は、必ず人が読む**。AI は、何が作られる・消されるかを、かみ砕いて説明する
2. **`apply` と `destroy` は、人が承認してから**実行する。勝手に実行させない
3. **コンソール（手作業）で作ったものと、Terraform で作ったものを混ぜない**。混ぜると、state とずれる
4. **権限は最小に**。学習用でも、本番に近づけるときは `AdministratorAccess` から絞る
5. **費用の予算（ゼロ支出予算・月次予算）を先に置く**。作ったら、使い終わったら `destroy`
6. 秘密の値（DB のパスワードなど）は、`.tfvars` や環境変数で渡し、**コミットしない**
7. 変更は、これまでと同じ **Issue → ブランチ → PR** で行う。Terraform のファイルも、レビューしてからマージする

## 9. 公開するときの、いちばん大事な注意
このアプリは、**自分のPCの中だけで使う前提**で作ってある。

- ログインがない
- バックエンドは `127.0.0.1` だけで待ち受けている
- `/api/backup` で、**全データの書き出し・入れ替えが、誰でもできる**

そのままインターネットに出すと、**知らない人に、データを見られたり、消されたりする**。
公開する前に、次のどれか（または組み合わせ）が必要になる。

- ログイン機能を足す
- 自分のIPアドレスからだけ、つなげるようにする（セキュリティグループなど）
- CloudFront や ALB の前に、認証をつける

これは**仕様の変更**になるので、やる前に、ユーザー（あなた）と相談して決める。詳しくは [docs/deploy-options.md](../docs/deploy-options.md)。
