# 08 AWS と Terraform でデプロイする：初めての人のための解説と手順

このアプリを、**AWS（アマゾンのクラウド）** に置いて、インターネットから使えるようにする。
ただし、AWS の管理画面（マネジメントコンソール）をポチポチ操作するのではなく、**コマンドと設定ファイル**で行う。それを AI（Claude Code）にやってもらう。
この章は、そのための**予備知識と、準備の手順**をまとめたもの。

> 状況（2026-10-28）：準備の段階。AWS には、まだ何も作っていない（費用ゼロ）。
> 認証の方式は、**まず講義と同じ「専用 IAM ユーザーのアクセスキー」**にする（SSO は、あとで試す）。デプロイ先の構成は、**講義を確認してから決める**。構成の候補は [docs/deploy-options.md](../docs/deploy-options.md)。

## 1. IaC（アイエーシー）とは
**Infrastructure as Code（インフラをコードで管理する）** の略。

「インフラ」とは、アプリが動くための土台のこと（サーバー、データベース、ネットワークなど）。
管理画面で手作業で作ると、次の困りごとがある。

| 手作業（管理画面） | IaC（コードで書く） |
|---|---|
| 何をクリックしたか、あとで分からなくなる | 設定ファイルが、そのまま記録になる |
| もう一度同じものを作るのが大変。ミスも起きる | 同じファイルを実行すれば、同じものができる |
| 誰が、いつ、何を変えたか分からない | Git で履歴が残る。PR でレビューもできる |
| 片付け忘れて、お金がかかり続ける | 1コマンドで、全部消せる |

つまり、このプロジェクトで、アプリのコードを Issue → PR で育ててきたのと**同じやり方を、インフラにも使える**、ということ。

## 2. AWS の基本用語
AWS には200以上のサービスがあるが、このアプリで関係しそうなものだけ、先に覚える。

| 用語 | 意味 | このアプリでは |
|---|---|---|
| **リージョン** | AWS の拠点の地域（東京は `ap-northeast-1`） | どこに置くか。日本から使うので、東京が候補（講義に合わせる） |
| **IAM** | 「誰が、何をしてよいか」を決める仕組み | 作成済みの `rie-admin` と、`Administrators` グループ |
| **ポリシー** | 許可・禁止のルールの書類 | `AdministratorAccess`、`DenyBillingAndAccountClosure` |
| **IAM ロール** | 人やサービスが、**一時的に**権限を借りる仕組み | サーバーに、必要な権限だけを持たせる |
| **S3** | ファイルを置く倉庫 | 画面（ビルドした HTML・JS・CSS）を置く |
| **CloudFront** | 世界中に、ファイルを速く配る仕組み（CDN） | 画面の配信。HTTPS にもできる |
| **EC2** | AWS 上の仮想サーバー（1台のパソコン） | バックエンド（Spring Boot）を動かす |
| **ECS / Fargate** | コンテナ（Docker）を、サーバー管理なしで動かす | バックエンドの置き場所の候補 |
| **RDS** | AWS が管理してくれるデータベース | PostgreSQL の置き場所の候補 |
| **VPC** | AWS の中の、自分専用のネットワーク | 外から見える所と、見えない所を分ける |
| **セキュリティグループ** | 通信の出入りの許可リスト（ファイアウォール） | 「DB には、サーバーからだけつなげる」など |
| **ALB** | 通信を、複数のサーバーに振り分ける入口 | バックエンドの入口の候補 |

覚え方：**「何を置くか」→ S3、「どこで動かすか」→ EC2 か ECS、「データはどこか」→ RDS か同居、「誰が触れるか」→ IAM とセキュリティグループ**。

## 3. AWS CLI とは
AWS を、**コマンドで操作する道具**。管理画面でできることは、ほぼ全部できる。

```
aws s3 ls                       自分の S3 の倉庫を一覧する
aws sts get-caller-identity     「いま、だれとして操作しているか」を確認する
```

`aws sts get-caller-identity` は、**まず最初に打つコマンド**。ログインできているか、別のアカウントを触っていないかを確かめられる（出てくるアカウント ID は、他人に見せない）。

Terraform も、実は、**裏で AWS CLI と同じ認証の情報を使って**、AWS とやり取りする。だから、先に AWS CLI の認証を整える。

## 4. Terraform とは
IaC の道具の1つ（HashiCorp 社製）。**「こういう状態にしたい」と設定ファイル（`.tf`）に書くと、AWS をその状態にしてくれる**。

### 4.1 用語
| 用語 | 意味 |
|---|---|
| **provider** | Terraform が、どのサービス（AWS など）を操作するかの部品 |
| **resource** | 作りたい物1つ（例：S3の倉庫1つ、EC2 1台） |
| **variable** | 設定ファイルに外から渡す値（例：リージョン） |
| **output** | 作ったあとに表示したい値（例：サーバーのアドレス） |
| **state（状態ファイル）** | 「Terraform が、いま何を作ったか」の記録（`terraform.tfstate`） |

設定ファイルの見た目（イメージ。これは**例**で、まだ作らない）：

```hcl
provider "aws" {
  region = "ap-northeast-1"
}

resource "aws_s3_bucket" "frontend" {
  bucket = "my-example-bucket-name"   # 世界で1つだけの名前にする
}
```

### 4.2 4つのコマンド（この順に使う）
| コマンド | 何をする | AWSに変化は？ |
|---|---|---|
| `terraform init` | 準備（provider の部品をダウンロード） | なし |
| `terraform plan` | 「こう変わります」という**予告**を表示 | なし |
| `terraform apply` | 予告どおりに、**実際に作る・変える** | **あり（費用が発生しうる）** |
| `terraform destroy` | 作ったものを、**全部消す** | **あり（削除）** |

**`plan` を必ず読む**。`+` は作る、`~` は変更、`-` は削除。「データベースが消える」ような行がないか、`apply` の前に人の目で確かめる。

### 4.3 state の注意
- state には、**パスワードなどの秘密が入ることがある**。このリポジトリは**公開**なので、`*.tfstate` は**絶対にコミットしない**（`.gitignore` で除外する）
- 本格的な運用では、state を S3 に置いて共有する。学習の最初は、手元のファイルでよい
- state を消す・失くすと、Terraform が「何を作ったか」を忘れる。AWS に物が残って、お金がかかり続けることがある

## 5. 認証：AWS に「自分だ」と伝える方法
AWS CLI と Terraform が、AWS を操作するには、**認証**が要る。方式は主に2つ。

| | IAM Identity Center（SSO） | アクセスキー |
|---|---|---|
| 仕組み | ブラウザでログインして、**数時間で切れる一時的な鍵**をもらう | 長い文字列の鍵（ID とシークレット）を PC に置く |
| 安全性 | 高い。PC に長期の鍵が残らない | 低め。**漏れると、他人が自由に使える** |
| 設定の手間 | やや多い（最初に Identity Center の設定が要る） | 少ない |
| 向いている場面 | 人が使う、普段の操作 | 古い仕組み。なるべく避ける |

方針（2026-10-28 に決定）：
- **まず、講義と同じ「専用 IAM ユーザーのアクセスキー」で進める**。仕組みが単純で、「認証とは何か」を体験できる。ルートユーザーのキーは、**絶対に作らない**
- **SSO は、あとで試す**（コースの最終課題などで。先生に聞いてみる）。どちらも経験しておく。認証の方式は、アプリのコードとは別の話なので、Terraform の `.tf` はほぼそのままで、切り替えられる
- 注意：アクセスキーは、**MFA では守れない**。漏れると、MFA に関係なく使われる。特にこのリポジトリは公開なので、キーを書いたファイルを誤ってコミットすると、数分で悪用されることがある。5.3 のルールを守る
- 参考：AWS CLI には、IAM ユーザーが「コンソールのログイン情報」で CLI にログインする機能（`aws login`）も、新しく追加されている。使うなら、公式ドキュメントで確かめてから

### 5.1 アクセスキー方式の手順（講義の方式）
1. AWS の管理画面（IAM）で、**CLI 用の IAM ユーザー**を作る（講義の例：`terraform-deployer`）。ログイン用のユーザー `rie-admin` とは、**別にする**
2. 作ったユーザーを、`Administrators` グループに入れる（請求と解約を禁止するポリシー `DenyBillingAndAccountClosure` が、同じように効く）。講義では `AdministratorAccess` を付ける（学習用。本番に近づけるときは、権限を絞る）
3. そのユーザーの「セキュリティ認証情報」から、**アクセスキーを作成**する（用途は「コマンドラインインターフェイス（CLI）」）。**アクセスキー ID とシークレットアクセスキー**が表示される。シークレットは、この画面でしか見られない
4. 手元で `aws configure` を実行して、4つを入力する：Access Key ID、Secret Access Key、リージョン（`ap-northeast-1`＝東京）、出力形式（`json`）
5. `aws sts get-caller-identity` で、作ったユーザーとして認識されているか確認する（結果のアカウント ID は、他人に見せない）

キーを表示する画面（3 の画面）は、**画面共有・スクリーンショットで、人やチャットに見せない**。

### 5.2 SSO を選んだ場合の手順（流れ。あとで試す）
1. AWS の管理画面で、IAM Identity Center を有効にして、ユーザーと権限（許可セット）を作る
2. 手元で `aws configure sso` を実行して、案内に従う（リージョンなどを聞かれる）。プロファイル名を決める（例：`taskboard`）
3. `aws sso login --profile taskboard` でブラウザが開く → ログイン（MFA も使う）
4. `aws sts get-caller-identity --profile taskboard` で確認
5. Terraform には、`AWS_PROFILE=taskboard` を環境変数で渡す、または provider に `profile = "taskboard"` と書く

### 5.3 認証の情報を守るルール（AI に任せるときも同じ）
- アクセスキー、アカウント ID、QR コード、パスワードを、**チャットに貼らない・リポジトリに入れない**
- キーは、`aws configure` が作るファイル（`~/.aws/credentials`）にだけ置く。メモ帳・文書・`.tf`・`.env` に書かない
- 使わなくなったら、キーを**無効化して削除**する（IAM の画面から）。コース修了後も、残さない
- 漏れたかもしれないと思ったら、すぐ IAM で**キーを無効化**して、ユーザーに相談する
- 認証の情報は `C:\Users\<ユーザー名>\.aws\` に保存される。ここは**コミットしない**（リポジトリの外にあるので、ふつうは入らない）
- 画面や出力を貼るときは、アカウント ID と ARN を**隠す**

### 5.4 `aws configure` とは
AWS CLI に「だれとして、どこで操作するか」を**覚えさせる**設定コマンド。1回やれば、次からは毎回入力しなくてよい。

| 質問 | 入れるもの | 講義の例 |
|---|---|---|
| AWS Access Key ID | キーの ID（`AKIA` で始まる） | IAM ユーザーで作ったもの |
| AWS Secret Access Key | 秘密のキー（パスワードに相当） | 同じ画面で表示されたもの |
| Default region name | 使う地域 | `ap-northeast-1`（東京） |
| Default output format | 結果の表示形式 | `json` |

- 保存先（リポジトリの外）：`C:\Users\<ユーザー名>\.aws\credentials`（**キーが入る。秘密**）と、`.aws\config`（リージョンと出力形式）
- AWS CLI と Terraform は、このファイルを自動で読む。だから、`aws s3 ls` や `terraform plan` で、キーを毎回入力しなくてよい
- 関連：`aws configure list`（今の設定を確認。シークレットは一部だけ表示される）、`aws configure --profile 名前`（別の設定を、名前をつけて作る。SSO を試すときに、分けて使える）
- 入力を間違えたら、もう一度実行すれば、上書きできる

### 5.5 SSO とは、アクセスキー方式との違い
**SSO（シングルサインオン）** は、1回ログインすれば、複数のサービスを使える仕組み。AWS では「IAM Identity Center」が担当する。ブラウザでログインすると、**数時間で切れる一時的な鍵**が PC に渡される。

| 項目 | アクセスキー方式（講義の方式） | SSO 方式（IAM Identity Center） |
|---|---|---|
| たとえ | 期限のない合鍵 | 今日だけ有効の入館証 |
| 鍵の期限 | なし（削除するまで有効） | 数時間で自動的に切れる |
| PC に残るもの | 長期の秘密（`~/.aws/credentials`） | 一時的な鍵だけ |
| ログインの方法 | 最初に `aws configure` で1回入力。あとは何もしない | 使うたびに `aws sso login`（ブラウザでログインと MFA） |
| MFA との関係 | **MFA では守れない**。キーだけで操作できる | ログイン時に MFA を使えるので、鍵の発行まで守られる |
| 漏れたときの被害 | 大きい。気づくまでずっと使われる | 小さい。数時間で切れる |
| 漏れたときの対処 | IAM でキーを無効化・削除 | 権限を取り消す。放っておいても期限で切れる |
| 設定の手間 | 少ない（IAM ユーザー → キー → `aws configure`） | 多い（Identity Center の有効化、ユーザー、許可セット、`aws configure sso`） |
| 使うたびの手間 | なし | 期限切れのたびにログイン |
| 向いている場面 | 手軽に始めたい学習。ロールや OIDC が使えない場所での自動化 | 人が普段使う操作、安全を重視する場面 |
| このプロジェクトでの扱い | まず、こちらで進める | あとで試す（最終課題などで） |

大事な違い：
1. **鍵が長持ちするか、すぐ切れるか**。アクセスキーは、漏れると長く悪用される
2. **MFA が効く場所**。アクセスキー方式では、MFA は管理画面のログインだけを守り、キー自体は守らない
3. **手間の置き場所**。アクセスキーは、最初が簡単で、あとは自分で気をつける。SSO は、最初が大変で、あとは仕組みが守る

同じところ：どちらも、AWS CLI と Terraform から同じように使える。Terraform の `.tf` は、ほぼ変えずに済む（変えるのは、認証の設定の部分だけ）。`aws sts get-caller-identity` で、どちらも確認できる。
なお、SSO は、IAM ユーザー（`rie-admin` など）とは**別の仕組み**で、Identity Center 側にユーザーを作る。

### 5.6 自動で動かすときの選択肢（アクセスキーしかない、ではない）
| 自動で動かす場所 | 推奨される方法 | 長期のアクセスキー |
|---|---|---|
| AWS の中（EC2、ECS、Lambda など） | **IAM ロール**を付ける。サーバーが自動で一時的な鍵を受け取る | 要らない |
| GitHub Actions など、外部の自動化 | **OIDC**（5.7） | 要らない |
| 上のどちらも使えない場所（自分の PC、他社のサーバーなど） | アクセスキー（または IAM Roles Anywhere） | 要ることが多い |

AWS は、自動化でも、**長期のキーを避ける**方向に進んでいる。アクセスキーは「昔からある、手軽な方法」であって、唯一の方法ではない。

### 5.7 OIDC とは（将来、GitHub Actions からデプロイするとき）
**OIDC（OpenID Connect）** は、「この人（や仕組み）は本物だ」と、別のサービスが**証明してくれる**仕組み。たとえるなら、合鍵を預ける代わりに、毎回「その日限りの紹介状」を出して、「その日限りの入館証」をもらうやり方。

流れ（GitHub Actions から AWS を操作する場合）：
1. GitHub Actions の実行が始まる
2. GitHub が、その実行専用の**短い期限の証明書（トークン）**を発行する（「このリポジトリの、この枝（ブランチ）からの実行」という情報入り）
3. 実行が、その証明書を AWS に見せる
4. AWS は、事前に登録した「GitHub を信用する」設定と、「この条件なら、この IAM ロールを使ってよい」という設定（信頼ポリシー）を照らし合わせる
5. 条件に合えば、**約1時間で切れる一時的な鍵**が渡される
6. その鍵でデプロイなどをして、終わったら、鍵は期限で消える

準備するもの：
- AWS 側：ID プロバイダーの登録（`token.actions.githubusercontent.com`）、IAM ロール（付ける権限と、信頼ポリシー）。Terraform でも書ける
- GitHub 側：ワークフローに `id-token: write` の権限を足す。公式の部品 `aws-actions/configure-aws-credentials` に、ロールを渡す

良い点：GitHub に**キーを保存しなくてよい**（漏れるものがない）。鍵が約1時間で切れる。「リポジトリ」「ブランチ」で、使える範囲をしぼれる。

注意：
- **条件のしぼり込みが甘いと危険**。リポジトリ名だけでなく、ブランチまで指定する。書き忘れると、他のリポジトリからも使える設定になる事故がある
- ロールの権限は、デプロイに必要な最小限にする
- このプロジェクトの今の CI は、権限が読み取りだけ（AWS も触らない）。OIDC を使うときは `id-token: write` を足すので、**やる前に相談する**（運用の変更）

このプロジェクトでは、今は不要。将来、GitHub Actions から自動でデプロイしたくなったら、アクセスキーを GitHub に置かずに、OIDC を使うのが安全。

### 5.8 jq とは（なくても困らない）
`jq`（ジェイキュー）は、JSON を整形したり、必要な部分だけを取り出したりする道具。AWS CLI の結果は JSON で返るので、`aws sts get-caller-identity | jq -r .Arn` のように、絞り込める（`|` は、左の出力を右に渡す）。

- **必須ではない**。AWS CLI にも、同じ絞り込みの機能（`--query`）が最初から付いている。例：`aws sts get-caller-identity --query Arn --output text`
- AI が `aws ... | jq ...` の形のコマンドを使うことがある。入れておくと、そのまま動く。入れるなら：`winget install jqlang.jq`（入れたあとは、ターミナルを開き直して、`jq --version`）

## 7. 最初の Terraform 体験（費用ゼロ）
まず、**AWS に何も作らない**操作だけで、流れを知る。

1. 空のフォルダ（このリポジトリの外でもよい）に `main.tf` を作り、provider だけを書く
2. `terraform init`：provider の部品がダウンロードされ、`.terraform/` ができる
3. `terraform validate`：書き方が正しいか調べる
4. `terraform plan`：何も作らないので、「変更なし」と出る

**ここまでなら、料金はかからない**。実際に作る体験（`apply`）は、10.2 に書いた。

## 8. AI（Claude Code）にデプロイさせるときの安全ルール
AI は速いが、間違えることもある。AWS は**お金がかかり、消すと戻らない**ので、次を守る。

1. **`plan` の結果は、必ず人が読む**。AI は、何が作られる・消されるかを、かみ砕いて説明する
2. **`apply` と `destroy` は、人が承認してから**実行する。勝手に実行させない
3. **コンソール（手作業）で作ったものと、Terraform で作ったものを混ぜない**。混ぜると、state とずれる
4. **権限は最小に**。学習用でも、本番に近づけるときは `AdministratorAccess` から絞る
5. **費用の予算（ゼロ支出予算・月次予算）を先に置く**。作ったら、使い終わったら `destroy`
6. 秘密の値（DB のパスワードなど）は、`.tfvars` や環境変数で渡し、**コミットしない**
7. 変更は、これまでと同じ **Issue → ブランチ → PR** で行う。Terraform のファイルも、レビューしてからマージする

## 9. 公開するときの、いちばん大事な注意
このアプリは、**自分のPCの中だけで使う前提**で作ってある。

- ログインがない
- バックエンドは `127.0.0.1` だけで待ち受けている
- `/api/backup` で、**全データの書き出し・入れ替えが、誰でもできる**

そのままインターネットに出すと、**知らない人に、データを見られたり、消されたりする**。
公開する前に、次のどれか（または組み合わせ）が必要になる。

- ログイン機能を足す
- 自分のIPアドレスからだけ、つなげるようにする（セキュリティグループなど）
- CloudFront や ALB の前に、認証をつける

これは**仕様の変更**になるので、やる前に、ユーザー（あなた）と相談して決める。詳しくは [docs/deploy-options.md](../docs/deploy-options.md)。

### 10.2 Terraform 段階1：空の EC2 を作って、確認して、消した（2026-10-30）
講義の方針（学習課題、無料の範囲、画面とサーバーを同じ EC2 に載せる、段階的に作る）に合わせて、**EC2 だけ**を作った。アプリのデプロイは、最後の工程なので、まだやっていない。

作ったもの（`terraform/` のコード。10個）：

| ファイル | 役割 |
|---|---|
| `main.tf` | 使う Terraform と AWS 部品の版、地域（東京）、共通のタグ |
| `variables.tf` | 外から渡す値（自分の IP、型、公開鍵の場所）。`my_ip` は、打ち間違いと `0.0.0.0` を弾く |
| `vpc.tf` | 自分専用のネットワーク（VPC、サブネット1つ、玄関＝インターネットゲートウェイ、道順の案内板＝ルートテーブル）。NAT Gateway は作らない |
| `security_groups.tf` | 通信の許可リスト。入口は **SSH（22番）を、自分の IP（`/32`）だけ**。出口は全許可 |
| `ec2.tf` | 公開鍵の登録、OS（Amazon Linux 2023）の探し方、EC2 本体（`t3.micro`、ディスク 20GB・暗号化、IMDSv2 必須）。`user_data` は付けない |
| `outputs.tf` | 作ったあとに、IP と SSH のコマンドを表示 |

進めた流れ：
1. 読み取りだけの事前確認：`aws ec2 describe-instance-types --filters Name=free-tier-eligible,Values=true` で、無料の対象の型を調べた。**このアカウントでは `t2.micro` は対象外で、`t3.micro` が対象**だった（先生の画面は `t2.micro`）
2. SSH の鍵を作った（`ssh-keygen -t ed25519`）。AWS に渡すのは、公開鍵（`.pub`）だけ。秘密鍵は、PC から出さない
3. `terraform.tfvars` に、自分の IP を書いた（`.gitignore` で除外。見本は `terraform.tfvars.example`）
4. `terraform init` → `fmt` → `validate` → `plan`。**`plan` を読んで、承認してから**、`apply`
5. 動作確認：22番に届くことと、`ssh` でログインして、`echo ok`、`logout` できることを確認した
6. 使い終わったので、`terraform plan -destroy` で予告を見て、承認してから、`terraform destroy`。10個すべてが消えて、AWS 上に残っていないことを、確認した

`plan` の読み方：
- `+` は作る、`~` は変更、`-` は削除。最後の `Plan: 10 to add, 0 to change, 0 to destroy.` を、まず見る
- `(known after apply)` は、「作ってみないと決まらない値」（ID や IP など）
- **入口（ingress）に `0.0.0.0/0` がないか**を確かめる。出口（egress）や道順（route）の `0.0.0.0/0` は、「外へ出ていく」方向なので、問題ない
- 同じ内容で実行したいときは、`plan -out=ファイル名` で保存して、`apply ファイル名` で実行できる（`*.tfplan` は、コミットしない）

つまずいた所と、学んだこと：
- **貼り付けの置き場所に注意**。`terraform.tfvars.example` の内容を、間違えてターミナルに貼ったところ、その後の `ssh-keygen` の「保存先は？」の質問に、貼った文字が入ってしまった。`Ctrl+C` で中止して、もう一度やり直した（鍵は、まだ作られていなかったので、被害はなし）。**ターミナルが何かの質問を待っているときは、貼り付けが、その答えになる**
- `Enter passphrase`：秘密鍵にかける「鍵のパスワード」。入力しても、画面には出ない（壊れたのではない）。忘れると、鍵を作り直しになる
- 初めて SSH でつなぐと、`The authenticity of host ... can't be established.` と出る。エラーではなく、「初めてのサーバーです。つなぎますか？」という確認。`yes`（3文字）と答える
- 接続すると、Amazon Linux 2023 のロゴ（鳥のような絵）が出る。`exit` で出ると、`logout` と `Connection to ... closed.` が出る（正常）
- 秘密で**ないもの**：公開鍵（`.pub`）、鍵の「四角い絵」（randomart）。秘密な**もの**：秘密鍵（拡張子なし）、パスフレーズ、アクセスキー
- **`destroy` で消しても、コードが残る**ので、また `plan` → `apply` で、同じ物をすぐ作れる（IP は変わる）。これが IaC の利点。ただし、`terraform.tfstate` は消さない
